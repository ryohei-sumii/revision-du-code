## 1. 実測結果 — 初めて"劣化"を観測 / Results: the first degradation

| 指標 | 値 | 過去（library 級）比 |
|---|---|---|
| **recall（per-run / majority）** | **0.67（14/21）／ 5/7** | **最低**（gin 12/12・axios 実質15/15・ripgrep 7/7） |
| **confident FP run 率** | **0.22（2/9）** | **field 史上初の非ゼロ**（過去は全て 0/N） |
| clean-run 率 | 0.44 | **最低**（ripgrep 0.67） |

**劣化は狭く・具体的——"認証/権限の業務ルール意味論"に集中。**
- **precision の2 FP は同一 fixture に集中**（`e49025c8`）: 権限（manage-rule）チェックを `OnRecordUpdateRequest` フックの
  外へ**意図的に移設**し、`LastSavedPK()`→`record.Id` に変更した実マージ commit。レビュアーは**意図的な権限ルール移設を
  "ID 上書き/権限バイパスのセキュリティバグ"と誤読**（＝本ラウンドが狩っていた失敗そのもの）。判定は**FP を洗浄せず正しく2件計上**。
- **recall の2 full miss（0/3）も認証意味論**: 認証 refresh/impersonate の refreshable-claim ゲート（#718）、realtime の
  `Unset(RealtimeClientAuthKey)`→`Unregister` すり替え（#5898）。**バグ版が"もっともらしい意図的な別実装"に見える**ため見逃し。
- **一方、同じアプリでも構造的バグは堅牢:** デッドロック（buffered→unbuffered channel）・panic-recover 除去・
  `sql.ErrNoRows` 区別除去・`if e.Auth != nil` ガード除去・nullifyMissingField 除去は**すべて 3/3 検出・FP 0**。

→ 弱点は**「アプリコード全般」ではなく「認証/権限の意味論的推論」というピンポイント**。

## 2. 判定 / Gate & assessment

**敵対ゲート `weaker-in-some-language`（＝messy-app/auth regime で明確に劣化）。** 「判定は保守的——2 FP を計上し洗浄せず、
曖昧な指摘を catch に誤認しない。**judging artifact でなく regime レベルの真の劣化**。Round 4 caveat を**closes でなく confirms**」。

**readiness `assistant-ready-with-caveats`（据え置き。ただし caveat が強く・具体的になった）。**
> 同じ messy アプリでも構造/crash/error/middleware バグは 3/3・FP 0 で堅牢、全体 majority 5/7＝**人間が vet する
> アシスタントとしては有用**。ゆえに not-ready には落とさない。だが**認証/権限の業務ルールコードでは precision・recall とも

## 3. スキル変更なし——なぜ変えないか（規律） / No change, and why

この劣化は実在するが、**安易なスキル修正はより危険**:
- **FP 側（意図的権限変更を過剰指摘）は"安全側"の誤り。** 「意図的に見える権限変更は指摘するな」というルールは、
  **本物の IDOR/認証バグの recall を直接危険にさらす**（標準則(a)が守る最重要クラス）。過剰指摘は人間トリアージで拾える。
- **recall 側（微妙な認証意味論の見逃し）はチェックリストで表現できる穴でなく、ドメイン判断の限界。** 綺麗な追記で直らない。
- しかも **n=1 fixture（2/3 run）・単一リポ**。8ラウンドの品質規律「**散発1件は改善対象でない／機構を足す前に再現を待て**」に従う。
  同じ「認証/権限移設 FP」が**別リポで再現**したら、そのとき初めて precision-safe な文面（例:「チェックの"移設"は"削除"では
  ない——どこへ行ったか追ってから bypass を主張せよ」）を検討する。

**成果は"スキル修正"でなく"信頼境界の地図＋運用指針":**
> **この tool は、アプリの認証/権限の業務ルール差分では最も当てにならない（誤報も見逃しも出る）。そこは人間が重点的に
> レビューせよ。** 構造/crash/error-handling/契約バグでは（アプリでも）信頼できる。

## 4. 学び / What this teaches

1. **"劣化する場所"を初めて特定できた——これが本ラウンド最大の価値。** 4ラウンドの library 級で 0-FP・高 recall を続けた後、
   狙って messy-app/auth regime を当てると**両軸で崩れた**。**負の結果こそ tool の信頼境界を描く**。過信を防ぐ。
2. **弱点はドメイン（認証/権限の意味論）であって"アプリ vs ライブラリ"ではなかった。** 同じアプリでも構造バグは堅牢。
   → 「アプリだから弱い」でなく「**曖昧で高文脈な業務ルールの意味論**（バグと意図が見分けにくい）で弱い」と精密化。
3. **誤報と見逃しが同じクラスに同居する。** 認証コードで「意図を過剰にバグ視（FP）」しつつ「バグを意図と誤認（miss）」——
   両方が**"意図と欠陥の区別"の難しさ**という単一原因に帰する。ここは**モデルのドメイン判断**の限界で、方法論では埋めにくい。
4. **規律: 実在の弱点でも、再現前・単一リポ・安全側の誤りには手を入れない。** 修正が最重要 recall を壊しうるなら、
   記録＋運用指針が正解。品質側8ラウンドの「単一フリップで機構を足さない」を field にも一貫適用。
