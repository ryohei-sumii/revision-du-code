# Field Round 8 — 候補文面の A/B 検証 / Testing the Fix（そして棄却）

**日付:** 2026-07-09 ／ **状態:** ✅ 完了・**スキル変更なし（候補文面を実測で棄却）** ／ 生データは本ラウンド workflow。

R7 で残存弱点（意図的に見える認証/可視性巻き戻しの見逃し）が言語一般と確定し、「編集を**検討**するバー」を満たした。
本ラウンドは規律に従い、**候補文面を足す前に A/B 実測**する——足せば効くという思い込みを排し、二軸で証明を求める。

---

## 1. 実験デザイン / What we A/B-tested

- **CUR:** 現行スキル（本物のファイルを読む）。**AUG:** 現行＋候補文面（下記）をレビュアーに追加提示。
- **候補文面（review-checklist.md 追記案）:** 「**認可/可視性/モデレーションの述語**で条件が除去/弱化されたら、単純化が
  意図的に見えても**誰のアクセス/可視性が広がるか**を述べてから受け入れよ。もっともらしい単純化でも access-control 回帰で
  ありうる。**精度ガード: 全述語変更を flag に反転するな**——追跡して access が広がらないなら fine と言え」。
- **2 fixture セット**（実 OSS・既存 fixture を流用）:
  - **miss セット（recall・5件）:** 過去に見逃した"意図的に見える"認証巻き戻し（mastodon block-policy／subscription-
    visibility、pocketbase auth-refresh-impersonate／auth-state-realtime、gitea access-anon-private）。
  - **precision セット（FP・4件）:** 意図的で正しい権限変更（R5 の FP fixture＝pocketbase 権限移設、gitea の権限リファクタ＋
    強化 fix 2件）。
- 各 fixture 各変種3 run。**採用条件: miss セットで recall↑ かつ precision セットで confident FP↑しない**——両立時のみ採用。
- 65エージェント・エラー0・3.54M tok。

## 2. 実測結果 — 候補は効かず / Results: the note did nothing

| 指標 | CUR | AUG | 差 |
|---|--:|--:|--:|
| **miss セット recall** | **0.23** | **0.17** | **−0.07（悪化）** |
| precision セット confident FP（run 数） | 3 | 3 | 0（横ばい） |

- **recall は上がらず、むしろ微減。** 改善した fixture は**ゼロ**、悪化2件（block-policy 3→2、gitea access-anon-private 1→0）。
  最も難しい2件（pocketbase auth-refresh-impersonate・auth-state-realtime）は**両変種とも 0/0**——狙った"意図的に見える"
  巻き戻しで候補は**何も買わなかった**。
- **precision は横ばい。** R5 の FP fixture（pocketbase 権限移設）は CUR/AUG とも 3/3 のまま（候補は新規 FP を生まず、既存も
  消さず）。gitea の正しい権限変更3件は両変種とも 0 FP。
- **敵対ゲート `reject`／判定 `reject-note`。** 「採用は recall↑×FP不増が条件。recall は満たすどころか反転（−0.07・改善0・
  悪化2）。precision 横ばいは guardrail であって、trade する recall 利得が無い以上、採用の理由にならない。**recall を払って
  何も買わない文面は棄却**——コストの hybrid を葬った規律のまま。」

**スキル変更なし。** 候補文面は不採用。

## 3. なぜ効かなかったか — 弱点はモデルの判断限界 / Why it failed

候補は「述語の条件が消えたら"誰の access が広がるか"を述べよ」と指示した。だが**効かなかった**。理由は本質的:
- **レビュアーは既に周辺コードを読んでいる。** それでも「バグ版が**もっともらしい設計判断に見える**」。追加の指示で
  "access が広がるか述べよ"と言っても、**まさにその判断（これは意図的な緩和か、回帰か）が難しい**のが弱点の核。
- つまりこの弱点は**チェックリストで埋まる"フックの欠落"ではなく、モデルの"意図と欠陥の弁別"というドメイン判断の限界**。
  L1（大標本）で埋めた C ヒープリークは「列挙漏れ＝フックの欠落」で**手法で直った**が、これは**手法では直らない**種類。
- **プロンプトで直せない弱点がある、と実測で確定した。** ゆえに残る緩和は唯一——**人間が認証/可視性差分を重点レビュー**する。

---

## 4. 学び / What this teaches

1. **"再現した弱点"にも、"効く修正"があるとは限らない——修正も測れ。** R7 で弱点は言語一般と確定したが、素直な候補文面は
   **recall を1ミリも上げなかった**。「弱点がある→文面を足す」は**思い込み**で、A/B が棄却した。**測らず足さない**を、
   コスト（hybrid）・品質（単一フリップ）に続き field でも貫いた。
2. **フックの欠落 vs 判断の限界を、実測が切り分けた。** L1 のヒープリーク＝手法で直るフックの欠落。本弱点＝手法で
   直らないモデル判断の限界。**"直せる穴"と"直せない限界"を区別する**のが誠実な工学。
3. **プロンプトで直せない限界の正しい扱いは「文面追加」でなく「境界の明示＋人間レビュー」。** 効かない機構を足すのは
   複雑化の純損。**限界を正直に文書化し、その差分は人間が見る**——これが over-engineering を避ける唯一の道。
4. **プロジェクト全体の一貫した真実:** 測って検証した機構は**ほぼ全て棄却か縮小された**——フル読込・hybrid・難度ルーター、
   そして本認証文面。**「機構を足す前に測れ／単純案が勝つ」が、品質・コスト・現場の3トラックすべてで再現**した。

## 5. Field 検証の最終到達点（8ラウンド・5言語）/ Final field standing

| R | 内容 | 結果 |
|---|---|---|
| R1-R4 | gin/requests/axios/ripgrep（4言語, lib） | 高 recall・0 FP・+latent |
| R5 | pocketbase（Go app） | 認証/権限で初の劣化 |
| R6 | gitea（Go app） | FP モードは**再現せず**（PocketBase 特有） |
| R7 | mastodon（Ruby app） | recall サブモードは**再現**（言語一般） |
| **R8** | **候補文面 A/B** | **効かず＝棄却**（弱点はモデル判断の限界） |

**総合 `assistant-ready-with-caveats`（人間トリアージ前提で実運用可）。確定した信頼境界:**
- **信頼できる（5言語・lib もアプリも）:** 構造・crash・並行・error-handling・契約バグ、および明白な認証バグ
  （IDOR・token-scope 等）。
- **確定した既知の限界（言語一般・プロンプトで直せない）:** 「意図的な別実装に見える微妙な認証/可視性/モデレーション
  巻き戻し」を ~1-2件/repo 見逃す。**候補文面は A/B で効果ゼロと実証** → スキルでは緩和できず、**人間が重点レビュー**。
- **残 caveat:** アプリ標本は Go 2＋Ruby 1＋各1リポ、N 小＝方向性の信号。
