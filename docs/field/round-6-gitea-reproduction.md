## 1. 実測結果 — R5 の弱点は再現しなかった / Results: it did NOT reproduce

| clean-run 率 | 0.58 | R5 0.44 |

**precision の"怖い半分"は再現せず（本ラウンドの主眼）:**
- **R5 で FP を出した fixture の直接アナログ**＝`gitea-correct-3607516ce284`（owner-team 権限ロジックの**意図的リファクタ／移設**、
  まさに「移設を削除と誤読」の罠）は **clean 3/3**。捏造バイパス主張ゼロ。
- 怖い強化コミット（token 交換のクライアント束縛・保護ブランチ直コミット緩和）も **0 FP**。**4 correct fixture 全12run で FP=0**。

  これは**実在の非対称性についての hedged Question**（その穴こそ別 fixture `122ebcf` の仕込みバグ）で、**捏造でなく正しく非 FP**。

**recall は健全:** IDOR org 列挙・fork-PR クロスリポ・token scope・permission read・http scope を**すべて 3/3 検出**。

**敵対ゲート `generalizes`:** 「R5 の劣化は実質 PocketBase 特有。gate した precision 失敗モードは不在、recall は健全帯。
認証/権限の弱点はドメイン一般としては再現しない」。

## 2. 判定と決定 — スキル変更なし（規律の勝利）/ Decision: no edit, discipline vindicated

**判定: precision-safe 文面（「チェックの"移設"は"削除"でない——どこへ行ったか追ってから bypass を主張せよ」）は
"検討に値しない"。** R5 はこの文面を「FP が別リポで**再現したら**」と条件付けた。結果は**逆**——gitea は移設を正しく追跡し、
意図的リファクタで黙った。**再現しない失敗を直す文面を足すのは不動機な機構**で、しかも R5 自身が「"意図的に見える権限変更を
指摘するな"系のルールは本物の IDOR/認証 recall を危険にさらす」と警告した——そのクラスを gitea では 5/6 で検出している。
→ **スキル編集なし。** 運用指針（認証/権限は最も当てにならない領域＝人間が重点レビュー）は維持するが、R5 より**穏当に補正**（下記）。

**これは方法論の勝利:** 「**再現を待ってから機構を足す**」という規律（コストトラックで hybrid を葬ったのと同じ）が、
**PocketBase のノイズへの過学習編集を未然に防いだ**。R5 で n=1 に飛びつかなかった判断が、R6 で正しかったと実証された。

## 3. R5 の信頼境界マップを補正 / Refining the R5 trust-boundary

R5 は「認証/権限は precision も recall も当てにならない」とした。R6 はこれを**過大評価だったと補正**:
- **precision（意図的権限変更での FP）:** R5 の懸念は**実質 PocketBase 特有**——gitea は意図的な権限移設/強化を 0 FP で
  さばき、同時に本物の IDOR/token-scope/アクセス制御バグを検出。→ **一般的な precision 問題ではない**。
- **recall（認証バグ検出）:** gitea では健全（IDOR・token-scope・クロスリポ・permission-read を 3/3）。R5 の 0.67 は
  部分的に repo 特有。
- **残る真の弱点（狭い）:** 「**バグ版が"意図的な別実装"に見える微妙な認証巻き戻し**」を時折見逃す（R5・gitea で各1件）。
  これは両ラウンドで再現＝**唯一の一貫した残存サブモード**。第3のリポで確認するまで"解決"とは呼ばない。

## 4. 学び / What this teaches

1. **再現ゲートが過学習編集を防いだ——これが本ラウンド最大の価値。** R5 の劇的な FP（2/9）は、第2リポで**再現しなかった**。
   もし R5 で即座にスキルを直していたら、**PocketBase 固有ノイズに過学習**し、しかも最重要の IDOR recall を危険にさらしていた。
   **「単一観測で機構を足すな・再現を待て」は、負の観測（劣化）にも等しく適用される。**
2. **劇的な単発結果ほど、再現で検算せよ。** R5 は「初の劣化」という強い結果だったが、その"怖い半分"は repo 特有だった。
   品質/コストで学んだ「単一フリップを機能と誤認するな」の**field 版**——単発の"劣化"も機能と同じく再現で確定する。
3. **残った弱点は狭く具体的:** 「意図的な別実装に見える微妙な認証巻き戻しの見逃し」のみが2リポで一貫。ここが認証コードで
   人間レビューを要する真の理由（precision の乱れでなく、この recall サブモード）。
4. **正の結果も負の結果も、同じ敵対＋再現の規律で扱う——それが誠実さ。** 「劣化を見つけた」で終わらせず「再現するか」を測り、
   しなければ主張を穏当に補正する。過大にも過小にも振れない。
