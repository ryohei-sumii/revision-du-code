# Round 2 — recall↔cost の振り子 / The Recall–Cost Pendulum (A/B, 敵対ゲート付き)

**日付:** 2026-07-07 ／ **状態:** ✅ 完了・**スキル変更あり（hybrid 採用）** ／
**手法:** 読込スコープ違いの2変種を実フィクスチャで走らせ、コスト（読んだファイル数）と
recall/precision を同時実測。別モデルの敵対ゲートを通ったものだけ採用。

Round 1 が特定した最大の削減レバー＝`SKILL.md §2`「周辺コードを読め」（＝recall を担う中核）を
**実際に削ったら何が起きるか**を測る本命ラウンド。品質側の敵対ループと同じ「測定→敵対検証→適用」。

---

## 1. 実験デザイン / What we A/B-tested

同一モデル（レビュアーは全部 Sonnet 5）で、**§2 の読込スコープだけ**を差し替えた2変種:

| 変種 | §2 の指示 | 想定 |
|---|---|---|
| **A（現状）** | フル読込: 周辺コードを必要なだけ開き、契約変更は呼び出し側を grep して読む | recall 高・コスト高 |
| **B（予算制）** | 予算制: 「差分が触れたファイル＋1ホップの直接呼び出し側だけ」。全コードベース読み禁止 | コスト低・recall は? |

- **フィクスチャ:** Opus が4つの現実的な小コードベース（Python 注文/在庫・Go 並行キャッシュ・
  TS 認証API・JS ジョブキュー）をディスクに生成。各3〜4個のバグを仕込み、**検出可能性でタグ付け**:
  - `in-diff` … 差分ハンクだけで見える（計7個）
  - `requires-surrounding-read` … 差分が触れない別ファイル（呼び出し側/呼び出し先/config/guard）を
    読まないと捕れない（計8個）← **予算制が最も傷つけると事前予想した本命クラス**
  - 精度テスト用に benign trap（ハンクだけ見ると誤報しそうだが実は正しい）も各1〜2個。
- **各変種 各フィクスチャ 2回**（非決定性対策）。レビュアーは**実ファイルを Read/Grep**し、
  指摘＋**実際に開いたファイル一覧（＝コスト計測）**＋grep回数を構造化報告。
- **敵対ゲート（Opus・high effort）:** 集計を渡し「予算制は品質を割に合わないほど削っているか」を
  **懐疑を既定に**検証。**判定（Opus・提案のみ・ファイル編集なし）**が adopt/reject/hybrid を決定。
- 規模: 26エージェント・エラー0・総 **881,594 tok**・237ツール・約27.9分。

## 2. 実測結果（生データ）/ Raw results

### ヘッドライン

| 指標 | A（フル） | B（予算制） | 差 |
|---|--:|--:|--:|
| **Recall（全体, 15チェック）** | **0.90** | **0.87** | −0.03（≈ 30本中1本 = ノイズ域） |
| ├ `in-diff`（7） | 1.00 | 0.93 | −0.07 |
| └ `requires-surrounding-read`（8） | **0.81** | **0.81** | **±0（本命クラスは不変）** |
| **平均読込ファイル数/回** | **6.13** | **4.75** | **−23%（コスト減）** |
| **Precision** | 0.97 | **1.00** | +0.03 |
| 誤検出（FP） | 1 | **0** | −1 |

### フィクスチャ別

| fixture | 仕込 | recall A | recall B | 読込 A | 読込 B | FP A | FP B |
|---|--:|--:|--:|--:|--:|--:|--:|
| py-orders（契約破壊） | 4 | 1.00 | 1.00 | 7.0 | 4.5 | 1 | 0 |
| go-cache（並行・無制限） | 4 | 0.75 | 0.63 | 5.0 | 4.0 | 0 | 0 |
| ts-auth（IDOR/guard別ファイル） | 4 | 1.00 | 0.88 | 5.5 | 4.5 | 0 | 0 |
| js-jobs（冪等性） | 3 | 0.83 | **1.00** | 7.0 | 6.0 | 0 | 0 |

**唯一の方向性ある後退:** go-cache の BUG2（無制限 goroutine ファンアウト＋タイムアウト無し＝並行・
`requires-surrounding-read`）が A 2/2 → B 1/2 に。ただし片方の run では B も検出。しかも同じクラスの
js-jobs BUG-1（冪等性）は逆に A 1/2 → B 2/2 と改善し、**クラス recall は 0.81 で相殺・不変**。
両変種とも取り逃した go-cache BUG1（store 無制限成長）は予算制のせいではなく**両者共通の盲点**。

## 3. 敵対ゲートの判定 / Adversarial gate

> **verdict: budget-acceptable.** 事前の懸念（予算制が `requires-surrounding-read` クラスを傷つける）を
> データが直接反証した——同クラスの recall は両変種とも 0.81 で同一（8バグ）。A が捕るバグで B が
> **ゼロに落ちたものは一つもない**（＝実際に失われた本物のバグはゼロ）。唯一の方向性後退（Go BUG2, 2/2→1/2）は
> 単一 run のフリップで、片方では検出、同クラス内で JS 冪等性バグの改善に相殺される。全体 −0.03 は
> 4フィクスチャ・2 run の標本で run 間ノイズの域。対して B は precision を 0.97→1.0 に上げ、唯一の誤検出を
> 消し、読込を23%削る。**コスト削減単独では本物のバグを通す言い訳にならないが、ここでは本物のバグは一つも
> 通っていない**——懐疑がデータに耐えなかった、というのが正直な敵対的所見。唯一の注意は小標本での並行1件の
> フリップ。

## 4. 判定と適用 / Decision — adopt-hybrid（スキル変更）

**判定（Opus, 提案のみ）: `adopt-hybrid`。** 純粋な予算制は節約を得るが、方向性後退が並行・
`requires-surrounding-read` バグ——**品質トラックの絶対則が「コストと引き換えにしてはならない」と定めた
まさにそのクラス**——に出た。クラス recall が不変なのは無関係な冪等性バグの改善で相殺されただけで、
並行**固有**の信号は実際に劣化し、標本はそれを「ノイズ」と断ずるには薄い。純予算制はそのクラスを運任せに
する。そこで**hybrid**: 予算制を既定にしつつ、**2つのトリガーでは読込を必須化**（予算を使い切っていても必ず読む）:

1. **契約/シグネチャ/guard の変更** — 呼び出し側を grep して読む（従来どおり）＋ auth/IDOR 疑いは guard 層を grep。
2. **並行/共有状態の変更** — spawn/bound/await するコードを読む（無制限ファンアウト・タイムアウト欠如・
   未 await・レースはハンクに見えず最上位severity）。

これで**節約のほぼ全部（自己完結ハンクは予算制のまま）を確保しつつ、読み飛ばしが「本物の見逃し」になる
少数のハンクだけ全読込に戻す**。純予算制より安全で、コスト差は小さい。`reject-budget` は不当——
フル読込の+23%コストはここでは測定可能な本物バグ recall を一切買っていない。

- **適用:** `SKILL.md §2` を上記 hybrid 文面に差し替え（本コミットに含む）。
- **副次効果:** 従来 §4 にあった「auth/IDOR は guard を grep」を §2 のトリガーへ引き上げ、
  「読む前に断定しない」規律と「読込予算」を一箇所に統合。

## 5. この計測が確立した学び / What this round teaches

（→ `cost-log.md §1` に 8〜10 として集約）

1. **recall↔cost の振り子は、思ったより非対称に振れる（＝安く削れる）。** 読込−23%に対し本物バグの
   recall 損失は実質ゼロ（−0.03 はノイズ、失われたバグ0）。しかも precision はむしろ改善。
   「読む＝コスト＝recall」の一次近似は粗く、**"どのハンクを読むか"を選べば、コストだけ落として
   recall を保てる**領域が実在する。削減の本丸は「読む量」でなく「読む対象の選別」。
2. **削っていい読込と、絶対削れない読込は"クラス"で分かれる。** 自己完結ハンク（整形・局所リファクタ）の
   周辺読込は捨ててよい。**契約変更**と**並行/共有状態**の周辺読込は捨てると本物を逃す。均一な
   「全部読め/予算内で読め」より、**トリガー起動の条件付き全読込**が最適。
3. **敵対ゲートは"通す"ためでなく"却下し損ねを防ぐ"ために効く。** ゲートは懐疑を既定にしたが、
   データが反証したので通した。逆に判定側は、ゲートが見た集計の**クラス内相殺**を見抜き（並行固有の
   劣化は生きている）、純予算制を却下して hybrid にした——**集計の平均は本物の後退を隠す**。
4. **コスト施策は品質施策と同じ敵対ループで検証できる（そして検証すべき）。** 片軸（コスト）を動かした
   反動（recall）は、品質側 Round 2 の「振り子の反動は測るまで見えない」の再現。実測なしに
   「予算制で十分」も「フル読込必須」も、どちらも当て推量だった。

## 6. 手法メモ / Methodology notes（AI 学習の記録）

- **コスト代理指標＝開いたファイル数。** Round 1 の「metered token は再送乗数3.7×でバイトから乖離」を踏まえ、
  本ラウンドは**エージェントが実際に Read したファイル数**を一次コスト指標にした（レビュアーが自己申告した
  file list、実在ファイルなので事後にバイトも検証可能）。トークン総額はハーネス usog（881k/26体）で把握。
  変種 A/B は**同一モデル・同一フィクスチャ**なので、差はスコープ指示のみに帰属する（交絡を排除）。
- **非決定性・位置バイアスへの対処:** 各セル2 run で非決定性を吸収（実際 go-cache BUG2・js-jobs BUG-1 が
  run 間でフリップ＝非決定性が観測された）。判定は**location＋欠陥主張**で厳格照合し、severity 文言は無視。
- **判定側のファイル先行編集を防止:** 判定エージェントに「提案のみ・編集禁止」を明示（品質側 R4/R7 で
  起きた「承認前の先行適用」の再発防止）。適用は本ラウンドの結論を受けて**人間側（このセッション）**が実施。
