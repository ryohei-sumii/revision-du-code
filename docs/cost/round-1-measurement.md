# Round 1 — 実測: 1回あたりトークンの計測ラウンド / Empirical Per-Run Measurement

**日付:** 2026-07-07 ／ **状態:** ✅ 完了 ／ **手法:** 実フィクスチャでスキルを走らせ実トークンを計測。

Round 0（`baseline-token-usage.md`）の**見積もりを実測で置換**する計測ラウンド。スキル本体は変更していない
（計測ラウンドゆえ提案0・変更0 — `cost-log.md §0` の予告どおり）。

---

## 1. 手法 / What we ran

- **フィクスチャ:** 現実的な小コードベース（Python の注文サービス、6ファイル/197行）を生成し、
  **小/中/大の3サイズの diff** を作成。相互参照あり（契約変更で呼び出し側 grep が発生する）。

  | フィクスチャ | diff行数(add+del) | 変更ファイル | DIFF.txt bytes | コードベース総bytes |
  |---|--:|--:|--:|--:|
  | small  | 12  | 1 | 1,155 | 6,261 |
  | medium | 65  | 4 | 4,261 | 8,197 |
  | large  | 197 | 8 | 9,380 | 11,517 |

- **計測:** 各フィクスチャを **2回ずつ**（非決定性対策）、計6体のレビュアーエージェントが
  **実際にスキルを忠実に実行**（SKILL.md + references を読み、DIFF を読み、`§2` に従い周辺コードを開き、
  指摘を出力）。各エージェントは①読んだ参照 ②開いた周辺ファイル ③grep回数 ④出力レビュー を構造化報告。
- **トークン算出:** **input** = 読まれた実ファイルのバイト（÷4）、**output** = workflow の `budget.spent()` 実測、
  **総計** = ハーネスの usage 計測（`subagent_tokens`）。ワークフロー全体で6体・エラー0・91ツール実行・約13.6分。

## 4. この計測が暴いた4つのコスト事実 / What measurement revealed

1. **レビュアーは diff サイズに関係なく毎回ほぼ全コードベースを読む。**
   small の **12行/1ファイル** diff でも全6ファイル読了。→ 周辺読込入力(1,565)は **diff 本体(289)の5.4倍**。
   ⇒ **可変費はコードベースの読込スコープに比例し、diff サイズには（小規模コードベースでは）比例しない。**
   Round 0 の「diff で強くスケール」は、小コードベースでは**反証**された。

2. **エージェント再送の乗数 ≈ 3.7×。** content 単一コピーの入力は ~8.6k tok なのに、metered input は ~31.5k。
   差は、**同じコンテキストが約15ツールターン（91/6）にわたり毎ターン再送**されるため（キャッシュで一部緩和）。
   ⇒ Round 0 の静的バイト計算では見えなかった**エージェント的コストの本体**。可変費の実額はここが効く。

3. **出力の約8割は推論＋ツール生成**で、最終レビュー文ではない。output 実測 7〜12k に対しレビュー文は 0.8〜1.6k。
   ⇒ 出力削減も「レビューを短く」より「**推論/ツール往復を減らす**（＝effort・往復数の制御）」が効く。

4. **メタコストは依然として桁違い。** 単発レビュー ~40k tok に対し、この計測ラウンド（6体）で 243.6k tok、
   改善1ラウンドは ~600k tok。**「使う」1回より「測る/改善する」1ラウンドが 6〜15倍。**

## 5. ドル換算（実測トークン基準）/ Cost in dollars

per-review の metered（input 31,524 / output 9,074）を各モデル単価で（**キャッシュ無し・リスト価格の上限**）:

| モデル（in/out per 1M） | 1回のレビュー | 備考 |
|---|--:|---|
| **Opus 4.8**（$5 / $25）| **≈ $0.38** | 計測はこの単価（エージェントはセッションモデル Opus 4.8 を継承）|
| Sonnet 5 導入価（$2 / $10）| ≈ $0.15 | **約60%減** |
| Sonnet 5 リスト（$3 / $15）| ≈ $0.23 | 約40%減 |

- **参考: 改善1ラウンド（~600k tok, Opus 混在, リスト上限）:** ≈ **$7.8**。

  プロンプトキャッシュ読み（≈0.1×）になり、実額はこれより低い（キャッシュ内訳はハーネス未提供のため未計上）。

## 7. 次ラウンドへの含意 / Implications for next round

実測が示した**最大の削減レバー**（優先度順）:

1. **周辺読込スコープの制御（recall↔cost の本丸）。** small で読込が diff の5.4倍。「差分が触れたファイル＋直接の
   呼び出し側だけ読む」等の予算制を入れ、**コスト減と recall 減を同時に実測**。品質側と同じ敵対ゲートで
   「割に合わない削り」を却下（次ラウンドの主眼）。
2. **エージェント再送乗数の圧縮。** キャッシュ活用（固定接頭辞の安定化）・ツール往復削減（一括読み）で
   metered input の 3.7× を下げる。プロダクト側だけでなくワークフロー側にも効く。
3. **難度に応じたモデル配分。** 単価差は実額で 40〜80%。機械的レビューを Sonnet/Haiku に寄せる余地
   （品質側の学び6「コスト＝品質でない」のコスト面での実額確認）。

生データは本ファイル、学びの集約は `cost-log.md` に追記。
