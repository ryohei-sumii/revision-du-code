## 2. 実測結果 — H と B は完全に同点 / Results — a dead tie

| 指標 | B 純予算 | H 修正 hybrid |
|---|--:|--:|
| Recall 全体（20チェック） | **0.87** | **0.87** |
| └ concurrency（9・本命） | **0.81** | **0.81** |
| └ contract-guard（5・非飽和） | **0.80** | **0.80** |
| └ other（6） | 1.00 | 1.00 |
| Precision | 0.98 | 1.00 |
| 誤検出（FP） | 1 | 0 |
| 平均読込ファイル数/回 | 5.60 | 5.07 |

**保護クラスのどれでも H は B を1ミリも上回らなかった**（concurrency 0.81=0.81・contract 0.80=0.80）。
差は二次的なもの（FP が py-threads の1件だけ H で消えた・読込がわずかに少ない）で、**hybrid の機構が
生んだ差ではない**（FP 差は1フィクスチャのノイズ、recall の利得ではない）。

### 目玉の反証: callee 読込ルールは1件も追加検出しなかった

H の看板だった「fire-and-forget は callee を読め」は、**5フィクスチャすべてで追加検出ゼロ**。理由は明快:

- **純予算制 B の定義「差分ファイル＋1ホップの呼び出し先/呼び出し元」に、callee 読込がすでに含まれている。**
  B は go-fanout の store.go、js-promises の store.js、py-threads の pool.py、ts-guard-hard の digestJob.ts を
  **毎 run 実際に開いて**、H と**バグごとに同点**で fire-and-forget を捕らえた（各 3/3）。
- 唯一 B が callee を読まなかった go-contract-hard の panic→error は **B=0/3・H=0/3**。H は指示どおり
  store.go/main.go を読み、run1 で破棄箇所を特定したが「実害なし」と Low-Nit に**格下げして見逃した**。
  → **読んでも捕れない**。override トリガーの問題は「読む/読まない」ではなかった。

## 3. 判定 — `simplify-to-budget`（ゲート・判定とも一致）/ Verdict

**敵対ゲート（Occam を既定）と判定（Opus・提案のみ）は独立に同じ結論に到達:**

> hybrid は保護クラスで B を上回って初めて追加の複雑さに見合う。どの軸でも上回らない。看板の callee 読込
> ルールは全フィクスチャで限界検出ゼロ——B が「純予算制」でありながら毎 run callee を読み、バグごとに H と
> 一致したため。複雑さは**未払い（unpaid）**。Occam により、保護クラスで明確な勝ちが無い以上、純予算制へ単純化。
> Round 3 の結論を大標本（3 run×5題材）で**再現**した。

**適用:** `SKILL.md §2` から「予算を override する2トリガー＋加算読込＋callee 読込」の機構を**撤去**し、
**純予算制**の平易な一段落へ差し替え（本コミット）。ただし品質ラウンドで得た severity 較正
——「**diff が壊した呼び出し側は"新規に導入したバグ"であり pre-existing ではない・full severity**」
（severity-rubric.md の "materially worse" carve-out）——は**明示的に温存**して単純化。並行/契約が
「予算を割く既定の場所」であることは §2 と §3 に残る。

**標準則との整合:** (a)「並行/セキュリティ/データ損失の recall をコストと引き換えにしない」——recall は
**バイト単位で同一**なので違反なし。(b) Occam——見合わない複雑さを削る。**両立**。

## 4. この計測が確立した学び / What this round teaches

（→ `cost-log.md §1` に 14〜15 として集約）

1. **「純予算制」は既に呼び出し先/元を読んでいる——だから override トリガーは重複だった。**（Round 4 実測・核心）
   B の「差分＋1ホップ」には caller/callee/guard の読込が**定義上含まれる**。hybrid が「必ず読め」と重ねて
   命じたトリガーは、**B が既にやっていること**の言い換えに過ぎず、追加 recall を生まなかった。
   **明示的な指示を足す前に、単純案が"暗黙に"それを満たしていないか測れ。**
2. **読ませても格下げすれば捕れない——recall の律速は"読む量"でなく"判断の較正"。**（Round 4 実測）
   go-contract-hard で H は callee を読んで破棄箇所を見つけたのに「実害なし」と Low-Nit に落として見逃した。
   周辺読込を強制しても、**severity 較正（"これは本物の欠陥か"の判断）が弱ければ recall は上がらない**。
   コスト側の「もっと読ませる」施策には recall 上の天井がある。次の伸びしろは読込量でなく判断側。
3. **自作機構は"再現"して初めて棄却できる。** Round 3 の「H は B に劣らない」を、標本を倍化し run を1.5倍にして
   **再現**——単発なら「小標本の綾」と抗弁できるが、2ラウンド連続なら結論は堅い。品質側の敵対ループと同じく、
   **棄却も1回でなく再現で確定する**。
