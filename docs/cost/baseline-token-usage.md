# Round 0 — 1回あたりトークン消費 ベースライン実測 / Per-Run Token Baseline

**日付:** 2026-07-07 ／ **対象:** `.claude/skills/code-review/`（品質収束後 = Round 8 時点のスキル一式）

コスト最適化を始める前の**現状のトークン消費**を実測・記録する。以降のラウンドは
このベースラインとの差分で語る。

> 前提: トークン数はオフラインのため厳密なトークナイザではなく、**2つの近似**
> （バイト÷4 と 語数×1.33）のレンジで示す。英語主体の指示文では両者は概ね ±15% に収まる。
> 数値は「桁とレンジ」を掴む目的であり、精密値ではない。

## 2. 1回のレビューの固定費 / Fixed cost per review

progressive disclosure により、指示は**必要になった段階で順に**載る。全部が同時に載るわけ
ではない。

| 段階 | 載るもの | tok（概算） | 備考 |
|---|---|--:|---|
| 常時 | `description`（system prompt） | ~85 | スキル一覧に常駐 |
| 発火 | `SKILL.md` 本体 | ~2,000 | トリガー時に本体が展開 |
| （スラッシュ時） | `commands/code-review.md` | ~250 | 自然言語起動なら不要 |
| §3〜§4 | `review-checklist.md` + `severity-rubric.md` | ~2,400 | レビュー中に Read |
| （任意） | `collect-diff.sh` ソース | ~650 | 実行のみなら 0。読む場合のみ加算 |

**固定オーバーヘッド ≈ 4.5〜5.4k tok（入力）。** しかもプロンプトキャッシュが効けば、この固定
分は**初回ターン以降ほぼ無料**になる。→ 固定費は既に小さく、削り代は乏しい（後述の学び1）。

## 3. 1回のレビューの可変費 / Variable cost per review（ここが支配的）

固定費より、**差分サイズと周辺コード読み込みに比例する可変費**が総コストを決める。可変費は
キャッシュされない実入力なので、そのまま課金対象。

| 項目 | コスト・ドライバ | 小（〜50行差分） | 中（〜300行 / 数ファイル） | 大（PR 2,000行+） |
|---|---|--:|--:|--:|
| `collect-diff.sh` の出力（diff 本体） | 差分の行数 | 0.4〜0.8k | 2〜4k | 15〜40k |
| 周辺コード Read（`SKILL.md §2`） | 開くファイル数・行数 | 3〜6k | 10〜20k | 25〜50k |
| 呼び出し側の Grep 確認（`§2` 契約変更時） | 契約変更の有無 | 0.3〜1k | 1〜2k | 2〜4k |
| 出力（指摘本文） | 指摘件数 | 0.3〜0.8k | 1〜1.5k | 1.5〜3k |

**1回あたり総トークン（桁の目安、入力+出力）:**

| 題材 | 概算合計 | 内訳の支配項 |
|---|--:|---|
| 小・限定差分 | **~10〜13k tok** | 周辺読み込み |
| 中規模 PR | **~20〜30k tok** | 周辺読み込み + diff |
| 大規模 PR | **~50〜90k tok** | diff + 周辺読み込み |

> 出力より**入力が支配的**（レビューは「大量に読んで少量書く」タスク）。よってコスト削減の
> 主戦場は出力短縮ではなく **入力（何をどれだけ読むか）の制御**。

## 4. 参考: 改善ワークフロー1ラウンドのメタコスト / Meta-cost of one improvement round

比較のため、**スキルを1回走らせる**コストと、**スキルを1ラウンド改善する**コストを並べる。桁が違う。

| | 1回のレビュー（プロダクト） | 1ラウンドの改善（メタ） |
|---|--:|--:|
| トークン | ~10〜90k | **~600k+**（R1 実測「約60万」） |
| エージェント数 | 1 | 20〜68（R1=20, R4=61, R5=68, R6=52, R7=59） |
| 所要 | 数十秒〜数分 | 約23分（R1 実測） |

- **1ラウンド ≈ 単発レビューの 10〜60倍**のトークン。8ラウンド累計は **~1,000万トークン規模**
  （推定 — 下記の計測ギャップ参照）。品質を収束させるために、単発レビュー数百〜千回分の
  コストを投じた、というのがこのプロジェクトのコスト実態。

## 5. 計測ギャップ（このベースライン自体の発見）/ Instrumentation gap

**改善ラウンドはトークンを一度も計測していなかった。** `docs/rounds/round-*-result.md` /
`*-eval.md` の該当欄は軒並み `subagentトークン: ?` の**プレースホルダのまま**。ハードな数値は
Round 1 の「約60万」ただ一つ。

→ 品質は recall/precision を第一級メトリクスとして測ってきたが、**コストは一度もメトリクス化
されなかった**。これはコスト・トラック最初の宿題そのもの:「測れないものは最適化できない」。
以降のラウンドは、各エージェント/各実行のトークンを**必ず記録**する。

## 6. ベースラインが示すコストの学び / Cost learnings from the baseline

1. **固定費は既に最適化済み — progressive disclosure がコスト対策も兼ねている。**
   スキル指示の総量は 23.7KB ≈ ~5〜6k tok だが、1回のレビューで常時載るのは `description`
   ~85 tok のみ。references（~2.4k）は**必要になって初めて**載り、キャッシュも効く。
   段階的開示は品質側では「中間忘却対策」だったが、**そのまま固定費の圧縮**でもある。
   → 固定費側に大きな削り代は無い。

2. **可変費（周辺コード読み込み）が総コストを支配し、それは品質ドライバと同一。**
   最大の可変費は `SKILL.md §2`「周辺コードを読んでから判断せよ」。この指示は recall/precision
   を上げる（ハンク単体で誤断しないため）**まさにその指示**が、最大のトークン消費源。
   → **これが本プロダクト固有の recall↔cost トレードオフ**。読み込みを削れば安くなるが、
   見落とし（false-negative）が増える。品質側の recall↔precision の振り子の、コスト版。

3. **入力支配・出力軽微。** コストはほぼ入力トークン（diff + 周辺読み込み）。削減の主戦場は
   「出力を短くする」ではなく「**何を読むかを賢く絞る**」。例: 差分の大きさに応じた読み込み
   予算、巨大 PR の分割、キャッシュの活用余地——が次ラウンドの探索対象。

4. **メタコスト >> プロダクトコスト。** 単発レビューは数銭〜十数銭規模だが、改善1ラウンドは
   その 10〜60倍、8ラウンドで ~1,000万トークン規模。**コスト最適化の投資対効果は「よく走る側
   （プロダクト）」に効く施策ほど高い**——1回の削減が使うたびに効くから。逆に、改善ループ
   自体のコストは「収束したら止める」（＝Round 8 の収束宣言）が最大の削減策だった。

## 次アクション / Next

- **[必須] 計測の実装。** 次のコスト・ラウンドは、実際にスキルを複数題材（小/中/大 diff）で
  走らせ、**実トークンを記録**してこのベースラインの見積もりを実測で置換する。
- **recall↔cost の振り子を測る。** 「周辺読み込みを予算で絞る」変更を入れ、コスト減と recall 減を
  同時に測定。品質側と同じ敵対的ゲート（別モデルが反証）で、**品質を割に合わないほど削る案を却下**。
