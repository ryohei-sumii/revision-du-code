# コードレビュースキル 改善ログ / Improvement Log

このスキル（`.claude/skills/code-review/`）を、**複数の AI モデルを敵対的に競わせて**
自己改善させた記録です。「何を・どう検証し・何を直したか」に加えて、その過程で得られた
**LLM（大規模言語モデル）についての学び**を残すことを目的にしています。

> 生きたログです。ラウンドごとに追記します。日付は各ラウンド見出しに記載。

---

## 0. 前提 — なぜ「検証」がそんなに重要なのか

このリポジトリの成果物は「コードレビューをさせるための指示書（スキル）」です。つまり
**プロンプト（自然言語の指示）そのものがプロダクト**です。プロンプトには次の厄介な性質が
あります。

- **正しさを直接コンパイル/テストできない。** コードなら型検査やユニットテストで機械的に
  検証できますが、「この指示文はレビュー品質を上げるか？」は実際に走らせて出力を観察する
  まで分かりません。
- **もっともらしく読めても、実際の挙動は逆のことがある。** 人間には良い指示に見えても、
  モデルは字面どおりに従い、意図と逆の結果を出すことがあります（後述）。

だからこそ「1体の AI が書いて自賛する」のではなく、**別のモデルに敵対的に反証させ、
反証を生き延びた改善だけ採用する**という検証設計を採りました。

## 1. 検証の設計 / What verification we ran

### 1.1 北極星（評価軸）
レビュー品質を、AI 評価でよく使う 2 軸に分解して固定しました。

| 軸 | 意味 | 悪い例 |
|---|---|---|
| **Recall（再現率 / 見逃さない力）** | 実際に存在する重大バグをどれだけ拾えるか | SQLインジェクションを見逃す |
| **Precision（適合率 / 誤検出しない力）** | 出した指摘のうち本物の割合 | 些細なスタイルを「重大」と誤報、根拠なき指摘 |

この 2 軸は**トレードオフ**の関係にあります（厳しくすると誤検出は減るが見逃しが増える、
など）。スキル設計の中心的な問いは「この 2 つをどう両立させる言い回しか」です。

### 1.2 3フェーズ構成（マルチエージェント・ワークフロー）

```
Critique（敵対的クリティーク）
   5つのレンズ × 別々のモデルが、スキルの弱点を赤チーム的に攻撃
        ↓  全結果を集約し重複除去（コードで実施）
Spar（壁打ち / 相互反証）
   各改善案を「提案したのとは別のモデル」が全力で論破しようとする
   → 自己攻撃を生き延び、recall も precision も害さない案だけ通過
        ↓
Synthesize（統合）
   生き残った改善だけを、既存の良さを壊さないよう1体が本体へ折り込む
```

**ポイント（AI 検証の勘所）:**
- **多様性の確保。** 同じモデルに何度聞いても似た盲点を共有します。あえて**役割（レンズ）も
  モデルも変える**ことで、1つの視点では見えない欠陥を炙り出します。
- **敵対的検証（adversarial verification）。** 「良い点を挙げて」ではなく「これは品質を下げる、
  と論破せよ」と反対向きに指示します。人は/モデルは肯定方向だと甘くなりがちなので、
  **反証を default にして初めて弱い改善案が淘汰されます。**
- **提案者 ≠ 検証者。** 壁打ちの相手は必ず別モデルに割り当て、自作自演の追認を防ぎました。

### 1.3 これらの弱点を検証設計にどう織り込むか（意識すべき点）

上記 7〜9 の性質は、**敵対評価そのものの信頼性**を左右します。だから設計に反映します。

- **非決定性 → 反復と合議で吸収。**
  単一の実行結果を鵜呑みにしない。複数モデル・複数レンズで独立に評価し、**反証を生き延びた
  ものだけ採用**する（1回の当たり外れをならす）。経験的評価（Round 2）でも、同じ差分を
  複数回・複数モデルで採点する。「1回失敗した＝欠陥」と早合点しない。
- **中間忘却 → 短く・分割・段階的開示。**
  各エージェントへの指示（プロンプト）を短く保ち、北極星・スキーマ・出力要件を**冒頭に集約**。
  スキル本体も薄く保つ。評価対象が長くなるほど中央が抜けることを前提に、**スコープを絞る**。
- **位置バイアス → 重要事項は端に、順序は入れ替える。**
  ワークフローの各プロンプトで、評価軸（recall/precision）と判定スキーマを**冒頭または末尾**に
  置く。審判に複数案を比較させる場面では**提示順をシャッフル**し、先頭・末尾の下駄を打ち消す。
  「提案者 ≠ 検証者」に加え、**同じ案を評価順の違う複数モデルに当てる**ことで位置効果を平均化。

> 要するに、AI に AI を検証させる以上、**検証者自身も非決定・中間忘却・位置バイアスを持つ**。
> だから「単発・長文・固定順」を避け、「反復・短文・順序かく乱・多モデル合議」を既定にする。

### 1.4 使ったレンズとモデル

| レンズ | 着眼点 | 担当モデル |
|---|---|---|
| recall | 重大バグの見逃しを生む言い回し・スコープの狭さ | Opus 4.8 |
| precision | 誤検出・些細指摘・根拠なき指摘・スコープ外の過剰指摘 | Sonnet 5 |
| prompt-efficacy | 指示がモデルを実際にうまく操縦できているか（レール化・逆効果） | Opus 4.8 |
| coverage | チェックリストの抜け・重大度表の較正・出力フォーマット | Sonnet 5 |
| mechanism | 差分収集スクリプトの死角（新規/リネーム/バイナリ/base誤り） | Haiku 4.5 |
| 壁打ち（反証側） | 上記各案を別モデルが論破 | 提案と別モデルを割当 |
| 統合 | 生存案の折り込み | Opus 4.8 |

> **コスト方針:** 最上位モデル Fable 5 は単価が高いため**不採用**。Opus 4.8 / Sonnet 5 /
> Haiku 4.5 の 3 モデルで多様性を確保。軽い機械的タスク（mechanism）は安い Haiku に寄せ、
> 難しい判断（recall・統合）は Opus に寄せる、という**タスク難度に応じたモデル配分**を実施。

## 2. AI についての学び / What this teaches about LLMs

このプロジェクトで実地に確認・活用した LLM の性質。今後の勉強の土台としてメモ。

1. **モデルは指示を「字面どおり」に守る。**
   「重大なものだけ報告して」と書くと、モデルは本当にそれ以外を黙って捨てます。結果、
   バグ発見能力自体は高いのに**報告される数（recall）が下がって見える**。逆に「絶対に
   MUST で指摘せよ」と煽ると誤検出（precision 低下）が増える。→ **指示の強さは出力分布を
   直接動かすツマミ**であり、慎重に較正すべき。

2. **「見つける」と「絞り込む」を同じ手順に混ぜると質が落ちる。**
   優れた設計は「まず幅広く洗い出す（recall 重視）→ 別ステップで信頼度・重大度で絞る
   （precision 確保）」と段階を分ける。1回で自己検閲させると、拾えたはずのバグを本人が
   握りつぶす。

3. **単一モデルの自己評価は当てにならない。**
   自分の書いた指示を自分で「良い」と言うのは容易。**独立した別モデルによる反証**を挟むと、
   もっともらしいが無益な改善が明確に淘汰される（＝アンサンブル/敵対的検証の効果）。

4. **多様性は "モデルを変える" と "役割を変える" の掛け算で作る。**
   温度やリトライで揺らすより、**異なる観点（レンズ）と異なるモデル**を組み合わせる方が、
   盲点被りを避けられる。

5. **プロンプトはコードと違い "実行して観察" が唯一の真の検証。**
   静的に読んで納得しても不十分。次ラウンドでは実際に**バグを仕込んだ差分でレビューを走らせ、
   拾えたか/誤報しなかったかをスコア化**する経験的評価に進む（下記 Round 2 予定）。

6. **コスト＝品質ではない。難度でモデルを配分する。**
   全部を最上位モデルにするのは無駄。機械的な確認は小型モデル、微妙な判断だけ上位モデル、
   という配分が費用対効果を最大化する。

7. **プロンプトは決定論的でない（non-determinism）。**
   同じ指示・同じ入力でも、実行のたびに出力は揺れる。`temperature=0` でも**完全な再現は
   保証されない**（サンプリング・実装・並列処理の非決定性が残る）。含意:
   - 1回の出力で「拾えた/拾えなかった」を断定してはいけない。**同じ検証を複数回・複数モデルで
     回し、多数決や合議**で判断する。
   - バグ検出の失敗が「スキルの欠陥」なのか「その回だけの揺らぎ」なのかを、単発では切り分け
     られない。**反復が前提。**

8. **中間忘却（lost-in-the-middle）。**
   長いコンテキストを与えると、モデルは**冒頭と末尾はよく覚えているが、真ん中の情報を
   取りこぼしやすい**。含意:
   - スキル本体（SKILL.md）を薄く保ち、詳細を参照ファイルに逃がす**段階的開示**は、単なる
     トークン節約ではなく**中間忘却対策**でもある（長い一枚岩の指示書は中央が死ぬ）。
   - レビュー対象の差分が巨大だと、中央付近の変更が手薄になる。→ スコープを絞る指示、
     大きい差分の分割の重要性。

9. **位置バイアス（positional bias / primacy・recency）。**
   モデルは**情報の「位置」に引きずられる**。最初（primacy）と最後（recency）を重視し、
   選択肢を評価させると**提示順が結果を変える**（先頭・末尾の候補が有利になりやすい）。含意:
   - **最重要の指示は冒頭か末尾に置く**（ゴール・制約・出力フォーマット）。中央に埋めない。
   - 審判（judge）に複数案を比べさせるときは**提示順を入れ替えて**位置の効果を打ち消す。
   - チェックリストの並び順が、拾われやすさに影響しうる（上位項目が優先されがち）。

## 3. ラウンド記録 / Round-by-round record

### Round 1 — 敵対的クリティーク → 壁打ち → 統合（完了）

- **状態:** ✅ 完了。詳細な生データは `rounds/round-1-critique.md` /
  `rounds/round-1-spar.md` / `rounds/round-1-result.md`。
- **入力:** 初版スキル一式。
- **規模:** エージェント20体（完了19・失敗1）、subagentトークン約60万、所要約23分。
- **流れ:** クリティーク **30件** → 重複除去 → 壁打ち上位 **14件** → 生存 **9件** を採用。
- **既知の欠測:** precision レンズ（Sonnet）の1体が構造化出力に5回失敗し欠測。
  → **非決定性（学び7）が実地に出た例。** 品質判断は残り4レンズ＋壁打ちで担保され、
  単一エージェントの失敗が全体を壊さない設計が機能した。

**採用した主な改善（すべて recall 改善・precision は害さないことを壁打ちで確認）:**

| 対象 | 改善（何を直したか） |
|---|---|
| `review-checklist.md` | 破壊的操作/データ損失のトリガを追加（無条件 DELETE/UPDATE/DROP、まだ読まれている列/ファイルの削除・リネーム）。重大度表の最上位 Critical に対応する検出トリガが本文に無かった穴を塞いだ。 |
| `severity-rubric.md` | ①「High はリソースリーク/状態不整合も含む」と是正（表の High 例＝ロック未解放と本文が矛盾していた）。②「セキュリティ/データ損失/並行性は Question でも1段上げ、確定指摘と同列に並べる」。③「差分が既存バグを新たに到達可能/悪用可能にした場合は本来の重大度で評価（Low に丸めない）」。 |
| `SKILL.md` | ①未確認でも重大クラス（security/data-loss/concurrency/crash）なら **Question として本来の重大度で報告**（nit に埋もれさせない）。②契約変更時は**呼び出し側を grep** して壊れた消費者を探す。③指摘フォーマットに**重大度ラベル必須**。④gotchas に**バイナリファイル**の扱いを追加。 |
| `commands/code-review.md` | 指摘フォーマットに重大度ラベルを追加（本体と整合）。 |

**この結果が示す AI の学び（追認）:**
- スキルは元々 precision ガードが厚く recall の錘が薄かった（＝「確証がなければ nit」で
  未確認の重大バグが消える）。→ **保守的フィルタが recall を抑える**（学び1）が現物で確認され、
  「未確認でも重大クラスは Question として本来の階層で」という**recall の counterweight**を追加。
- 生存9件すべてが recall を上げ precision を下げない、と別モデルが壁打ちで判定 →
  **敵対的検証（学び3）が「recall と precision のトレードオフを両立させる案」だけを通した。**

### Round 2 — 経験的評価（完了）

- **状態:** ✅ 完了。生データは `rounds/round-2-eval.md` /
  `rounds/round-2-fixtures.md` / `rounds/round-2-result.md`。
- **狙い:** 「読んで良さそう」を超えて**実際のレビュー品質を測る**。意見でなく測定値で駆動。
- **手法:** バグを仕込んだリアル差分＋無害トラップを4領域で Opus が作成 → Sonnet が独立検証で
  正解確定 → **現行スキルをそのまま** Opus/Sonnet/Haiku にレビューさせ → Sonnet が正解と照合し
  recall/precision を採点。位置バイアス対策で「順序無視・意味で照合」を審判に明示。

**実測スコア（現行スキル＝Round 1適用済み）:**

| 指標 | 値 | 内訳 |
|---|---|---|
| **Recall（見逃さない力）** | **0.80** | 仕込みバグ照合 12/15 |
| **Precision（誤検出しない力）** | **0.84** | 誤検出 4／全指摘 25 |
| extra_valid | 8 | 正解表に無いが本物の指摘（＝仕込み以外も拾えている） |
| 有効フィクスチャ | 3/4 | contract-break 1件が構造化出力5回失敗で欠測 |

- **取りこぼし:** logic-error×2, resource-exhaustion×1（＝副次バグ中心）。
- **誤検出の主因（4件中3件が同型）:** バインド変数（`LIMIT ?` 等）に型検証が無いのを
  **SQLi と誤報**／認可ミドルウェアが diff に見えないだけで **IDOR を definite High と断定**。

**採用した改善（2件・いずれも precision 改善／recall 中立、壁打ち通過）:**

| 対象 | 何を直したか |
|---|---|
| `review-checklist.md` | **「バインド変数はインジェクションのシンクではない」**を明記（`?`/`$1`/名前付きプレースホルダは型検証欠如でも SQLi にしない、型不一致クラッシュは高々 Low）。ただし**資源枯渇の軸は分離して保持**（値が無検証で巨大/負なら Medium）。 |
| `SKILL.md §4` | **「見えない欠陥を断定するな」の逆命題**を追加。認可欠如/IDOR の疑いはまず**ガード層(デコレータ/ミドルウェア)を grep**、見つかれば取り下げ、探して無ければ full severity、確認不能なら **definite High でなく Question** で本来の重大度＋具体シナリオ付き。 |

**この結果が示す AI の学び（最重要）:**
- **recall と precision は振り子。片方を意見だけで押すと、もう片方が黙って犠牲になる。**
  Round 1 は recall を積極的に上げた（Question を本来重大度で／セキュリティは1段上げ）。その
  **副作用として precision が漏れた**ことを、Round 2 の**実測が定量的に捕捉**（バインド変数の
  SQLi 誤報、IDOR の過断定）。Round 2 は precision 側を締め直した。
  → **「良くなったはず」は測るまで分からない。経験的評価が振り子の反動を可視化する（学び5）。**
- **非決定性が再発（学び7）:** contract-break フィクスチャが構造化出力5回失敗で1件欠測。
  Round 1 と同型の事象。**アンサンブルが吸収**し、残り3フィクスチャで測定は成立。
- **敵対検証が過学習を防いだ:** 診断2案はいずれも「たった数回の実行への過学習では？」という
  反証を課され、**data に支持され既出でない案のみ**通過（学び3）。

## 4. 用語ミニ辞典 / Glossary

- **Recall（再現率）** … 存在する問題のうち拾えた割合。高い＝見逃しが少ない。
- **Precision（適合率）** … 出した指摘のうち本物の割合。高い＝誤検出が少ない。
- **Adversarial verification（敵対的検証）** … ある主張を肯定するのではなく、**反証を試み**、
  反証に耐えたものだけ採用する検証法。
- **Ensemble / cross-model（アンサンブル・複数モデル）** … 複数モデルの独立判断を突き合わせ、
  単一モデルの偏りを打ち消す手法。
- **Railroading（レール化）** … 手順を細かく縛りすぎて、モデルの判断力を殺してしまう指示。
- **Progressive disclosure（段階的開示）** … 本体（SKILL.md）を薄く保ち、詳細は参照ファイルに
  分けて必要時のみ読ませる構成。トークン節約とトリガー精度の両立。
