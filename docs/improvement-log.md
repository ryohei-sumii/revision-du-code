# コードレビュースキル 改善ログ / Improvement Log

このスキル（`.claude/skills/code-review/`）を、**複数の AI モデルを敵対的に競わせて**
自己改善させた記録です。「何を・どう検証し・何を直したか」に加えて、その過程で得られた
**LLM（大規模言語モデル）についての学び**を残すことを目的にしています。

> 生きたログです。ラウンドごとに追記します。日付は各ラウンド見出しに記載。

---

## 0. 前提 — なぜ「検証」がそんなに重要なのか

このリポジトリの成果物は「コードレビューをさせるための指示書（スキル）」です。つまり
**プロンプト（自然言語の指示）そのものがプロダクト**です。プロンプトには次の厄介な性質が
あります。

- **正しさを直接コンパイル/テストできない。** コードなら型検査やユニットテストで機械的に
  検証できますが、「この指示文はレビュー品質を上げるか？」は実際に走らせて出力を観察する
  まで分かりません。
- **もっともらしく読めても、実際の挙動は逆のことがある。** 人間には良い指示に見えても、
  モデルは字面どおりに従い、意図と逆の結果を出すことがあります（後述）。

だからこそ「1体の AI が書いて自賛する」のではなく、**別のモデルに敵対的に反証させ、
反証を生き延びた改善だけ採用する**という検証設計を採りました。

## 1. 検証の設計 / What verification we ran

### 1.1 北極星（評価軸）
レビュー品質を、AI 評価でよく使う 2 軸に分解して固定しました。

| 軸 | 意味 | 悪い例 |
|---|---|---|
| **Recall（再現率 / 見逃さない力）** | 実際に存在する重大バグをどれだけ拾えるか | SQLインジェクションを見逃す |
| **Precision（適合率 / 誤検出しない力）** | 出した指摘のうち本物の割合 | 些細なスタイルを「重大」と誤報、根拠なき指摘 |

この 2 軸は**トレードオフ**の関係にあります（厳しくすると誤検出は減るが見逃しが増える、
など）。スキル設計の中心的な問いは「この 2 つをどう両立させる言い回しか」です。

### 1.2 3フェーズ構成（マルチエージェント・ワークフロー）

```
Critique（敵対的クリティーク）
   5つのレンズ × 別々のモデルが、スキルの弱点を赤チーム的に攻撃
        ↓  全結果を集約し重複除去（コードで実施）
Spar（壁打ち / 相互反証）
   各改善案を「提案したのとは別のモデル」が全力で論破しようとする
   → 自己攻撃を生き延び、recall も precision も害さない案だけ通過
        ↓
Synthesize（統合）
   生き残った改善だけを、既存の良さを壊さないよう1体が本体へ折り込む
```

**ポイント（AI 検証の勘所）:**
- **多様性の確保。** 同じモデルに何度聞いても似た盲点を共有します。あえて**役割（レンズ）も
  モデルも変える**ことで、1つの視点では見えない欠陥を炙り出します。
- **敵対的検証（adversarial verification）。** 「良い点を挙げて」ではなく「これは品質を下げる、
  と論破せよ」と反対向きに指示します。人は/モデルは肯定方向だと甘くなりがちなので、
  **反証を default にして初めて弱い改善案が淘汰されます。**
- **提案者 ≠ 検証者。** 壁打ちの相手は必ず別モデルに割り当て、自作自演の追認を防ぎました。

### 1.3 これらの弱点を検証設計にどう織り込むか（意識すべき点）

上記 7〜9 の性質は、**敵対評価そのものの信頼性**を左右します。だから設計に反映します。

- **非決定性 → 反復と合議で吸収。**
  単一の実行結果を鵜呑みにしない。複数モデル・複数レンズで独立に評価し、**反証を生き延びた
  ものだけ採用**する（1回の当たり外れをならす）。経験的評価（Round 2）でも、同じ差分を
  複数回・複数モデルで採点する。「1回失敗した＝欠陥」と早合点しない。
- **中間忘却 → 短く・分割・段階的開示。**
  各エージェントへの指示（プロンプト）を短く保ち、北極星・スキーマ・出力要件を**冒頭に集約**。
  スキル本体も薄く保つ。評価対象が長くなるほど中央が抜けることを前提に、**スコープを絞る**。
- **位置バイアス → 重要事項は端に、順序は入れ替える。**
  ワークフローの各プロンプトで、評価軸（recall/precision）と判定スキーマを**冒頭または末尾**に
  置く。審判に複数案を比較させる場面では**提示順をシャッフル**し、先頭・末尾の下駄を打ち消す。
  「提案者 ≠ 検証者」に加え、**同じ案を評価順の違う複数モデルに当てる**ことで位置効果を平均化。

> 要するに、AI に AI を検証させる以上、**検証者自身も非決定・中間忘却・位置バイアスを持つ**。
> だから「単発・長文・固定順」を避け、「反復・短文・順序かく乱・多モデル合議」を既定にする。

### 1.4 使ったレンズとモデル

| レンズ | 着眼点 | 担当モデル |
|---|---|---|
| recall | 重大バグの見逃しを生む言い回し・スコープの狭さ | Opus 4.8 |
| precision | 誤検出・些細指摘・根拠なき指摘・スコープ外の過剰指摘 | Sonnet 5 |
| prompt-efficacy | 指示がモデルを実際にうまく操縦できているか（レール化・逆効果） | Opus 4.8 |
| coverage | チェックリストの抜け・重大度表の較正・出力フォーマット | Sonnet 5 |
| mechanism | 差分収集スクリプトの死角（新規/リネーム/バイナリ/base誤り） | Haiku 4.5 |
| 壁打ち（反証側） | 上記各案を別モデルが論破 | 提案と別モデルを割当 |
| 統合 | 生存案の折り込み | Opus 4.8 |

> **コスト方針:** 最上位モデル Fable 5 は単価が高いため**不採用**。Opus 4.8 / Sonnet 5 /
> Haiku 4.5 の 3 モデルで多様性を確保。軽い機械的タスク（mechanism）は安い Haiku に寄せ、
> 難しい判断（recall・統合）は Opus に寄せる、という**タスク難度に応じたモデル配分**を実施。

## 2. AI についての学び / What this teaches about LLMs

このプロジェクトで実地に確認・活用した LLM の性質。今後の勉強の土台としてメモ。

1. **モデルは指示を「字面どおり」に守る。**
   「重大なものだけ報告して」と書くと、モデルは本当にそれ以外を黙って捨てます。結果、
   バグ発見能力自体は高いのに**報告される数（recall）が下がって見える**。逆に「絶対に
   MUST で指摘せよ」と煽ると誤検出（precision 低下）が増える。→ **指示の強さは出力分布を
   直接動かすツマミ**であり、慎重に較正すべき。

2. **「見つける」と「絞り込む」を同じ手順に混ぜると質が落ちる。**
   優れた設計は「まず幅広く洗い出す（recall 重視）→ 別ステップで信頼度・重大度で絞る
   （precision 確保）」と段階を分ける。1回で自己検閲させると、拾えたはずのバグを本人が
   握りつぶす。

3. **単一モデルの自己評価は当てにならない。**
   自分の書いた指示を自分で「良い」と言うのは容易。**独立した別モデルによる反証**を挟むと、
   もっともらしいが無益な改善が明確に淘汰される（＝アンサンブル/敵対的検証の効果）。

4. **多様性は "モデルを変える" と "役割を変える" の掛け算で作る。**
   温度やリトライで揺らすより、**異なる観点（レンズ）と異なるモデル**を組み合わせる方が、
   盲点被りを避けられる。

5. **プロンプトはコードと違い "実行して観察" が唯一の真の検証。**
   静的に読んで納得しても不十分。次ラウンドでは実際に**バグを仕込んだ差分でレビューを走らせ、
   拾えたか/誤報しなかったかをスコア化**する経験的評価に進む（下記 Round 2 予定）。

6. **コスト＝品質ではない。難度でモデルを配分する。**
   全部を最上位モデルにするのは無駄。機械的な確認は小型モデル、微妙な判断だけ上位モデル、
   という配分が費用対効果を最大化する。

7. **プロンプトは決定論的でない（non-determinism）。**
   同じ指示・同じ入力でも、実行のたびに出力は揺れる。`temperature=0` でも**完全な再現は
   保証されない**（サンプリング・実装・並列処理の非決定性が残る）。含意:
   - 1回の出力で「拾えた/拾えなかった」を断定してはいけない。**同じ検証を複数回・複数モデルで
     回し、多数決や合議**で判断する。
   - バグ検出の失敗が「スキルの欠陥」なのか「その回だけの揺らぎ」なのかを、単発では切り分け
     られない。**反復が前提。**

8. **中間忘却（lost-in-the-middle）。**
   長いコンテキストを与えると、モデルは**冒頭と末尾はよく覚えているが、真ん中の情報を
   取りこぼしやすい**。含意:
   - スキル本体（SKILL.md）を薄く保ち、詳細を参照ファイルに逃がす**段階的開示**は、単なる
     トークン節約ではなく**中間忘却対策**でもある（長い一枚岩の指示書は中央が死ぬ）。
   - レビュー対象の差分が巨大だと、中央付近の変更が手薄になる。→ スコープを絞る指示、
     大きい差分の分割の重要性。

9. **位置バイアス（positional bias / primacy・recency）。**
   モデルは**情報の「位置」に引きずられる**。最初（primacy）と最後（recency）を重視し、
   選択肢を評価させると**提示順が結果を変える**（先頭・末尾の候補が有利になりやすい）。含意:
   - **最重要の指示は冒頭か末尾に置く**（ゴール・制約・出力フォーマット）。中央に埋めない。
   - 審判（judge）に複数案を比べさせるときは**提示順を入れ替えて**位置の効果を打ち消す。
   - チェックリストの並び順が、拾われやすさに影響しうる（上位項目が優先されがち）。

## 3. ラウンド記録 / Round-by-round record

### Round 1 — 敵対的クリティーク → 壁打ち → 統合（完了）

- **状態:** ✅ 完了。詳細な生データは `rounds/round-1-critique.md` /
  `rounds/round-1-spar.md` / `rounds/round-1-result.md`。
- **入力:** 初版スキル一式。
- **規模:** エージェント20体（完了19・失敗1）、subagentトークン約60万、所要約23分。
- **流れ:** クリティーク **30件** → 重複除去 → 壁打ち上位 **14件** → 生存 **9件** を採用。
- **既知の欠測:** precision レンズ（Sonnet）の1体が構造化出力に5回失敗し欠測。
  → **非決定性（学び7）が実地に出た例。** 品質判断は残り4レンズ＋壁打ちで担保され、
  単一エージェントの失敗が全体を壊さない設計が機能した。

**採用した主な改善（すべて recall 改善・precision は害さないことを壁打ちで確認）:**

| 対象 | 改善（何を直したか） |
|---|---|
| `review-checklist.md` | 破壊的操作/データ損失のトリガを追加（無条件 DELETE/UPDATE/DROP、まだ読まれている列/ファイルの削除・リネーム）。重大度表の最上位 Critical に対応する検出トリガが本文に無かった穴を塞いだ。 |
| `severity-rubric.md` | ①「High はリソースリーク/状態不整合も含む」と是正（表の High 例＝ロック未解放と本文が矛盾していた）。②「セキュリティ/データ損失/並行性は Question でも1段上げ、確定指摘と同列に並べる」。③「差分が既存バグを新たに到達可能/悪用可能にした場合は本来の重大度で評価（Low に丸めない）」。 |
| `SKILL.md` | ①未確認でも重大クラス（security/data-loss/concurrency/crash）なら **Question として本来の重大度で報告**（nit に埋もれさせない）。②契約変更時は**呼び出し側を grep** して壊れた消費者を探す。③指摘フォーマットに**重大度ラベル必須**。④gotchas に**バイナリファイル**の扱いを追加。 |
| `commands/code-review.md` | 指摘フォーマットに重大度ラベルを追加（本体と整合）。 |

**この結果が示す AI の学び（追認）:**
- スキルは元々 precision ガードが厚く recall の錘が薄かった（＝「確証がなければ nit」で
  未確認の重大バグが消える）。→ **保守的フィルタが recall を抑える**（学び1）が現物で確認され、
  「未確認でも重大クラスは Question として本来の階層で」という**recall の counterweight**を追加。
- 生存9件すべてが recall を上げ precision を下げない、と別モデルが壁打ちで判定 →
  **敵対的検証（学び3）が「recall と precision のトレードオフを両立させる案」だけを通した。**

### Round 2 — 経験的評価（完了）

- **状態:** ✅ 完了。生データは `rounds/round-2-eval.md` /
  `rounds/round-2-fixtures.md` / `rounds/round-2-result.md`。
- **狙い:** 「読んで良さそう」を超えて**実際のレビュー品質を測る**。意見でなく測定値で駆動。
- **手法:** バグを仕込んだリアル差分＋無害トラップを4領域で Opus が作成 → Sonnet が独立検証で
  正解確定 → **現行スキルをそのまま** Opus/Sonnet/Haiku にレビューさせ → Sonnet が正解と照合し
  recall/precision を採点。位置バイアス対策で「順序無視・意味で照合」を審判に明示。

**実測スコア（現行スキル＝Round 1適用済み）:**

| 指標 | 値 | 内訳 |
|---|---|---|
| **Recall（見逃さない力）** | **0.80** | 仕込みバグ照合 12/15 |
| **Precision（誤検出しない力）** | **0.84** | 誤検出 4／全指摘 25 |
| extra_valid | 8 | 正解表に無いが本物の指摘（＝仕込み以外も拾えている） |
| 有効フィクスチャ | 3/4 | contract-break 1件が構造化出力5回失敗で欠測 |

- **取りこぼし:** logic-error×2, resource-exhaustion×1（＝副次バグ中心）。
- **誤検出の主因（4件中3件が同型）:** バインド変数（`LIMIT ?` 等）に型検証が無いのを
  **SQLi と誤報**／認可ミドルウェアが diff に見えないだけで **IDOR を definite High と断定**。

**採用した改善（2件・いずれも precision 改善／recall 中立、壁打ち通過）:**

| 対象 | 何を直したか |
|---|---|
| `review-checklist.md` | **「バインド変数はインジェクションのシンクではない」**を明記（`?`/`$1`/名前付きプレースホルダは型検証欠如でも SQLi にしない、型不一致クラッシュは高々 Low）。ただし**資源枯渇の軸は分離して保持**（値が無検証で巨大/負なら Medium）。 |
| `SKILL.md §4` | **「見えない欠陥を断定するな」の逆命題**を追加。認可欠如/IDOR の疑いはまず**ガード層(デコレータ/ミドルウェア)を grep**、見つかれば取り下げ、探して無ければ full severity、確認不能なら **definite High でなく Question** で本来の重大度＋具体シナリオ付き。 |

**この結果が示す AI の学び（最重要）:**
- **recall と precision は振り子。片方を意見だけで押すと、もう片方が黙って犠牲になる。**
  Round 1 は recall を積極的に上げた（Question を本来重大度で／セキュリティは1段上げ）。その
  **副作用として precision が漏れた**ことを、Round 2 の**実測が定量的に捕捉**（バインド変数の
  SQLi 誤報、IDOR の過断定）。Round 2 は precision 側を締め直した。
  → **「良くなったはず」は測るまで分からない。経験的評価が振り子の反動を可視化する（学び5）。**
- **非決定性が再発（学び7）:** contract-break フィクスチャが構造化出力5回失敗で1件欠測。
  Round 1 と同型の事象。**アンサンブルが吸収**し、残り3フィクスチャで測定は成立。
- **敵対検証が過学習を防いだ:** 診断2案はいずれも「たった数回の実行への過学習では？」という
  反証を課され、**data に支持され既出でない案のみ**通過（学び3）。

**採用した改善（2件・多フィクスチャ×クロスモデルで壁打ち通過、review-checklist.md）:**

| 種別 | 何を直したか |
|---|---|
| **recall** | 入力検証の項を3サブ項目に拡張: **アンカー欠如**(部分一致バイパス)/**no-op サニタイズ**(パターンが対象文字に当たらない・unicode soft hyphen等)/**過度に緩いマッチ**。真の regex 正しさ穴を狙う。 |
| **precision** | ReDoS の項を**実証ゲート付き**で追加: 「本当に曖昧分割があり、かつ**病的入力を実際に提示できる時のみ**指摘。ネスト量指定子だけでは不十分・提示できなければ Question 止まり、Critical/High にしない」。エンジン緩和は副次チェック。**素朴ルールと逆に precision を上げる**。 |

**この結果が示す AI の学び（最重要）:**
- **多フィクスチャは「ノイズ」と「本物の穴」を分離する。** 単発フィクスチャの低スコアに飛びつくと過学習。

- **素朴な recall 対策は precision を壊しうる。** 「ネスト量指定子=ReDoS」は直感的だが、多くは無害で、
  ルール化すると誤検出が増える。**実測が"直感の罠"を定量的に示し、実証ゲート付きの正しい形へ導いた。**
- **実行に基づく検証が効く。** 審判が正規表現を実際に走らせて良性と確認 → 静的な思い込みを覆した。
  「プロンプトは実行して観察が唯一の真の検証（学び5）」がクラス単位でも成立。

**この再確認が確立した学び:**
- **収束は"当てた題材分布上"の収束——分布を広げると新しい穴が出る。** 合成小標本（主に汎用/Go/Python）では出なかった
  C/手動メモリの穴が、多言語大標本で1件出た。**"収束"は「これ以上の穴が無い」でなく「今の題材では割に合う変更が無い」**。
- **穴は"モデル能力"でなく"スキルのフック"だった。** 見逃しは mechanical で Opus/full は捕れた＝スキル文の列挙漏れ。
  **方法論側にまだ埋められる穴が（分布を広げれば）残る**——学び「recall の律速はモデル」の**例外**（列挙漏れは手法で直る）。
- **大標本の主目的は"数字を締める"だけでない——新カテゴリの発見。** CI を狭める以上に、**未カバー分布の系統ギャップを
  1件でも掘り当てる**ことが大標本の価値だった。

## 現場検証 / Field Validation (Round 1 — 実 OSS gin)

合成でない**実リポジトリ**での初の検証（詳細は `docs/field/round-1-gin.md`）。`gin-gonic/gin` の実際の bug-fix
コミットを**逆適用**して"バグ再注入差分"を作り、**本物のスキルを読ませた Sonnet 既定構成**でレビュー。正解＝現実の
landed fix。合成の限界（合成≠実・採点者が LLM・仕込みバグは易しい）を閉じる狙い。

- **結果:** 実バグ **12/12 検出（per-run も majority も 1.00）**、全クラス（crash/nil/concurrency/contract/security/
  error-handling/correctness）、**クリーン差分の誤報 0/5**。敵対ゲートが生 diff を独立再読して**採点の水増しなしを確認**
  （`judging-sound`）。判定 = **`assistant-ready-with-caveats`**。スキル変更なし（現場性能の測定）。
- **学び:**
  1. **"実用に耐える"は3つの別主張——今回は1つ目を強く実証した。** 「実コードの既知バグ回帰を捕まえる」≠「新規の
     組織的バグを見つける」≠「危なく見える正しい差分で黙る」。実 OSS 12/12・誤報0・敵対通過は合成では得られない前進
     だが、**汎用 recall 保証ではない**。
  2. **良い field テストは"正解"の設計が9割。** landed-fix を正解に使い（＋テスト hunk 除去）、敵対ゲートが生 diff を
     独立再読することで、**LLM 採点でも客観に近い**測定になった。
  3. **次の最大の未測定軸は precision——"実質的だが正しい"リファクタでの誤報。** 今回の 0/5 は自明 benign（docs/typo/
     version）限定。FP 疲れ＝採用可否を決めるのは"危なく見えるが正しい大改修"での誤報で、それは未測定。
  4. **severity 較正は要監視。** High の nil-handler panic を 2/3 run が低 severity に誤格下げ（検出はできた）。
     自律ゲートには「検出＝十分」でない。n=1 のためスキルは変えず監視対象に。

### Field Round 2 — precision / 誤報疲れ（実 OSS gin・正しい実変更）

Round 1 が残した最大の穴＝「**危なく見えるが正しい実コード**での誤報率（FP 疲れ＝採用可否を決める軸）」を測定
（詳細 `docs/field/round-2-gin-precision.md`）。gin にマージされ生存した実質的リファクタ/perf/型・シグネチャ変更/並行/
security 13件（正解=正しい）＋隠し実バグ4件を、本物のスキルで各3run レビュー。**スキル変更なし（測定ラウンド）**。

- **結果:** 正しい実変更で **clean run 46%・0.64指摘/レビュー・confident-FP run 率 0.13**（真値はさらに低い）、
  隠し positive は **4/4 検出**（低 FP は沈黙で買っていない）。敵対ゲート `judging-sound`。判定
  `assistant-ready-with-caveats`（precision 軸が測定され強かった・残る caveat は外部妥当性）。
- **学び:**
  1. **FP 疲れの本命軸で"静かで的確"。** 採用を左右する実質変更で、口を開けば大半が本物の潜在バグか妥当な観察、
     真ノイズは 39run で~2〜3件。**recall・precision の両軸が実コードで検証された**（Round 1 の最大の穴が埋まった）。
  2. **"マージ済み＝正しい"は漏れる。** レビュアーが"正しい"集合から **14件の本物潜在バグ**を発見（1件は gin が後に
     実修正=#4702 の chmod）。→ field の precision 数値には**正解自身の誤りという系統ノイズ**が乗る。公平な判定＋
     敵対再検証が要る。これは同時に、planted でない**organic バグ発見能力の直接証拠**（難しい主張への現場肯定）。
  3. **残る摩擦は"意図的破壊変更"の指摘**（検出漏れでなく framing の問題）。n=2・単一リポのため過学習回避で監視のみ。

**Field 到達点（2ラウンド）:** 「実用に耐える」の3主張のうち①実害バグ検出（12/12＋4/4）②正しい変更でノイズを撒かない
（clean 46%・低 FP）を実コードで強く実証。③organic バグ発見も14件の latent 検出で部分裏付け。総合
`assistant-ready-with-caveats`（人間トリアージ前提のアシスタントとして実運用可）。残 caveat は外部妥当性（多言語・
大差分・非リプレイ・severity 較正）で、precision/recall の欠陥ではない。

### Field Round 3 — 多言語（Python requests ＋ JS axios）

Round 1/2 が残した最大 caveat＝「単一言語（Go/gin）」を、別言語の実 OSS で検証（詳細
`docs/field/round-3-multilang.md`）。同一手法（bug-fix 逆適用＝recall／マージ済み実変更＝precision）を
Python `requests`・JS `axios` に適用。**スキル変更なし**。

- **結果:** Python recall 0.87（majority 4/5・唯一の miss は `__getattr__` duck-typing の本質的難所）、JS 実質
  **15/15=1.00**（生 0.83 は退化フィクスチャ1件のため）。precision は JS がよく標本化されクリーン（clean 0.92・FP 0.08）、
  Python は n=1 で薄いが再び **Critical 潜在バグ（共有 SSLContext）を検出**。敵対ゲート `generalizes`。判定
  `assistant-ready-with-caveats`。
- **学び:**
  1. **コア挙動（実バグ回帰を捕え・正しいリファクタで黙る）が Go/Python/JS の3言語で再現。** 単一言語 caveat は
     実質的に弱まった。
  2. **ただし"言語×リポ"の交絡は未解決**——各言語1リポ（全て成熟 HTTP ライブラリ）。caveat は消えず性質が変わっただけ。
     過信は禁物（caveat を「単一言語」→「3言語だが各1ライブラリ・Python 標本薄」に格下げ）。
  3. **"マージ済み≠バグ無し"が別言語でも再現**（requests の"正しい"perf commit で Critical 潜在バグ 3/3）。organic
     バグ発見の追加証拠＋正解汚染の言語横断性。
  4. **方法論: fixture の質が数字を左右する。** 挙動不変の退化フィクスチャ1件が JS recall を 1.00→0.83 に見せた。
     → 逆適用差分が**本当に挙動を変えるか**の fixture QA を今後入れる。Python の duck-typing miss は n=1・本質的難所の
     ため監視のみ（スキル不変）。

**Field 到達点（3ラウンド）:** ①実害バグ検出 ②正しい変更でノイズを撒かない ③organic バグ発見 を **3言語**（Go/
Python/JS）で実証。残 caveat は「各言語1ライブラリ・Python 標本薄・大差分/非ライブラリ未検証・severity 較正」＝
カバレッジであり、precision/recall の欠陥ではない。

### Field Round 4 — Rust ＋ 非ライブラリ（ripgrep CLI）

Round 3 が残した2 caveat（未検証言語・ライブラリ限定）を同時に叩く（詳細 `docs/field/round-4-rust-ripgrep.md`）。
Rust 製 CLI `ripgrep` に同一手法。**スキル変更なし**。

- **結果:** recall 0.90（**majority 7/7**・crash/correctness/regex/**memory-refcycle**/escaping）、confident FP **0/12**、
  clean 0.67（非 clean は自己申告 Nit のみ）。**Arc vs Weak 参照循環**を検出＝Rust 固有の所有権推論。判定
  `assistant-ready-with-caveats`（敵対ゲートは agent エラーで null、assess が自己批判的に代替）。
- **学び:**
  1. **4言語目で"未検証言語"caveat がクローズ。** Go/Python/JS/Rust でコア挙動が一貫。Rust 固有推論（Arc/Weak・スライス
     panic）まで通用＝元3言語への過学習でない証拠。
  2. **"アプリ"caveat は看板倒れになりうる。** ripgrep は CLI だがバグ表面は library 級 crate で例外的に高テスト。
     → 「非ライブラリ」から「**雑然/低テストのアプリ未検証**」へ caveat を精密化（消えていない・FP が最も出る領域）。
  3. **replay の易しさは recall を過大評価する。** 既知修正の逆適用は novel バグより局所的で易しい。field recall は上振れと読む。
  4. **前ラウンドの保留2件を解消:** requests 共有 SSLContext 指摘は本物（=2.32.0 #6667 の実 SSL 回帰）→ Python 0-FP 保持。
     escaping fixture の dir タイポは判定に非汚染（DIFF＋指摘から正しく caught 3/3）。

**Field 到達点（4ラウンド・4言語）:** ①実害バグ検出 ②正しい変更でノイズを撒かない ③organic バグ発見 を Go/Python/JS/
Rust で実証。総合 `assistant-ready-with-caveats`。残 caveat は「各言語1リポ・**雑然/低テストの本物のアプリ未検証**・
replay≤novel・大差分・severity 較正」＝カバレッジで、精度/再現率の欠陥ではない。

### Field Round 5 — 業務ロジック・アプリ（PocketBase）＝**初めて劣化を観測**

Round 4 が残した最後の caveat（雑然/業務アプリ）を狙い撃ち（詳細 `docs/field/round-5-pocketbase-app.md`）。Go 製
バックエンドアプリ pocketbase の認証/権限/レコード業務ロジックに同一手法。**precision フィクスチャは"意図的だが怖く見える"
権限リファクタ**を投入。**スキル変更なし**。

- **結果:** recall **0.67（majority 5/7・最低）**、confident FP **0.22（field 史上初の非ゼロ）**、clean 0.44。
  **劣化は"認証/権限の意味論"にピンポイント集中**——2 FP は意図的な権限チェック移設をセキュリティバグと誤読、2 miss は
  意図的別実装に見える認証状態の巻き戻し。**一方、同じアプリでも構造/crash/error/middleware バグは 3/3・FP 0 で堅牢。**
  敵対ゲート `weaker-in-some-language`、判定 `assistant-ready-with-caveats`（caveat を confirms・精密化）。
- **学び:**
  1. **"劣化する場所"を初めて特定＝本ラウンド最大の価値。** 負の結果こそ tool の**信頼境界**を描く。過信を防ぐ。
  2. **弱点はドメイン（認証/権限の意味論）であって"アプリ vs ライブラリ"ではない。** 同じアプリでも構造バグは堅牢。
     「バグと意図が見分けにくい高文脈な業務ルール」で弱い。
  3. **誤報と見逃しが同クラスに同居**——「意図を過剰にバグ視(FP)」しつつ「バグを意図と誤認(miss)」＝**"意図と欠陥の
     区別"の難しさ**という単一原因。モデルのドメイン判断の限界で、方法論では埋めにくい。
  4. **規律: 実在の弱点でも、再現前・単一リポ・"安全側の誤り"には手を入れない。** FP 抑制ルールは最重要の IDOR/認証 recall を
     壊しうる。→ スキル修正でなく**信頼境界の地図＋運用指針**が正解（8ラウンドの「単一フリップで機構を足さない」を field にも適用）。

**Field 到達点（5ラウンド）— 信頼境界の地図:**
- **信頼できる（lib もアプリも・4言語）:** 構造・crash・並行・error-handling・契約バグ。
- **当てにならない（人間が重点レビュー）:** **認証/権限の業務ルール意味論**（誤報も見逃しも出る）。
- 総合 `assistant-ready-with-caveats`。残 caveat: アプリ標本 n=1・真の低テスト雑コード未検証・N 小＝**方向性の信号**。

## 4. 用語ミニ辞典 / Glossary

- **Recall（再現率）** … 存在する問題のうち拾えた割合。高い＝見逃しが少ない。
- **Precision（適合率）** … 出した指摘のうち本物の割合。高い＝誤検出が少ない。
- **Adversarial verification（敵対的検証）** … ある主張を肯定するのではなく、**反証を試み**、
  反証に耐えたものだけ採用する検証法。
- **Ensemble / cross-model（アンサンブル・複数モデル）** … 複数モデルの独立判断を突き合わせ、
  単一モデルの偏りを打ち消す手法。
- **Railroading（レール化）** … 手順を細かく縛りすぎて、モデルの判断力を殺してしまう指示。
- **Progressive disclosure（段階的開示）** … 本体（SKILL.md）を薄く保ち、詳細は参照ファイルに
  分けて必要時のみ読ませる構成。トークン節約とトリガー精度の両立。
