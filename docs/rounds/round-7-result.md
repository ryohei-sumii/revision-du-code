## 壁打ち(反証 1件)

### 1. verdict=**revise** recall:neutral / precision:improves / data支持:True / 既出:False
- 反論: Checked both reference files: neither "documented precondition/GIVEN" nor "unsubstantiated external fact (driver semantics, runtime-version default, public-API status)" is covered anywhere today — review-checklist.md only has the unrelated "trust boundary" line for validation, and severity-rubric.md has nothing on this. So the gap is real and not a duplicate of existing text. The evidence is also genuinely cross-cutting: the two named sub-patterns (JitterPct precondition; math/rand seeding) each reproduce on two different models on the same fixture, and the "unsubstantiated external fact" sub-pattern additionally reproduces on two other, unrelated fixtures (gen-errorhandling/opus's driver-abort-semantics claim, gen-mixed/sonnet's offset-is-a-public-API claim) — three separate fixtures, three models, not a single cherry-picked run.

However, the proposed remedy has a concrete hole exposed by the evidence itself. For sub-pattern (2), the proposal's remedy is "drop it or raise a Question at the severity it would carry if true." But the gen-nits/sonnet false positive that this clause is meant to fix was *already* framed as a Question ("hedged as a 'Question'... effectively flagging a benign trap as a plausible bug") and the eval still counted it as a false positive. That means the "or raise a Question" branch of the proposed fix does not reliably close the very gap it cites as evidence — a model following the new instruction to the letter could pick the Question branch and reproduce the identical failure. The instruction needs to distinguish: (a) facts that reflect the current, well-established default of a language/runtime (e.g., Go has auto-seeded the global `math/rand` source since 1.20, which shipped years ago and is now the overwhelmingly common case) — these should be *assumed true and dropped*, not hedged, unless the diff/repo shows concrete evidence of an older target (e.g., an old `go.mod` version); vs (b) facts that are genuinely bimodal/deployment-specific (which SQL driver is in use, whether a parameter is a published public API) — where "raise a Question at the severity it would carry if true" is legitimate and doesn't cost recall. Collapsing both into one remedy under-fixes case (a), which is exactly the reproducing example cited.

Also worth flagging: this evidence set includes a companion FP the proposal explicitly does NOT target (gen-nits/opus's "Max cap applied after jitter defeats jitter at the ceiling" design critique) which is a different failure mode (asserting a design flaw on a clean fixture, not a precondition-violation or external-fact claim) — so the "6 of 8" framing is accurate and the proposal author correctly scoped around it; no over-claiming there.
- 応答: The core direction survives scrutiny: this is a real, reproducible, currently-uncovered gap (verified by grep — not redundant with the existing trust-boundary or "READ, not downgrade" language, which only covers reading unshown *repo* code, not unconfirmable *external* facts like runtime-version defaults or driver semantics). The fix is tightly scoped to two narrow assumption types and explicitly preserves the existing Question-at-severity mechanism for genuinely uncertain externalities, so it shouldn't meaningfully cost recall on real security/data-loss/concurrency findings. The one real defect is that "raise a Question" is offered as an equally-valid escape hatch for cases where the evidence shows Question-hedging already failed to prevent the false positive. Tightening the wording to bias toward an outright drop when the assumed fact contradicts a current well-established default (mirroring the file's own existing "well-established language/runtime semantics" exception, just applied in the opposite direction — to debunk rather than confirm) closes that hole without adding scope, and actually *reuses* language already present in the same section 4 paragraph, keeping net bloat low.
