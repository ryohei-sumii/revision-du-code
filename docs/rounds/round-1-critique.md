## CRITICAL (1)

### Confidence and severity are conflated, routing confirmed-but-hard-to-articulate bugs into 'Nit'
- **file**: `.claude/skills/code-review/SKILL.md`  |  **category**: railroading
- **evidence**: SKILL.md line 66: 'Only claim something is a bug if you can name how it breaks; otherwise mark it as a question or a nit.' plus severity-rubric.md lines 15-16: 'A finding is at least High only if you can name a concrete input/state that produces a wrong result. If you can't, it's a Question or a Nit.'
- **なぜ品質を下げるか**: An AI follows this literally. Many genuine high-severity defects (a data race, a subtle off-by-one spanning two functions, an auth check bypassable in a way that is obvious but tedious to build an exact payload for) are recognizable without the reviewer being able to hand-author the precise triggering input within the review budget. The rule makes inability-to-name-an-exact-input LOWER the severity, and explicitly offers 'nit' as a destination. Since Nit is defined as 'Maintainability only; no behavior impact', a real behavioral bug lands under a label that tells the maintainer it has no behavior impact, so they skip it. This is the largest recall leak in the skill: it buries true positives under the lowest-priority heading.
- **提案**: Split confidence from severity into two independent axes. Instruct: 'Severity = how bad it is IF real. Confidence = how sure you are. Inability to name an exact triggering input lowers your CONFIDENCE (report it as a Question at the severity it would carry if confirmed, e.g. "Question / likely High") — it never lowers severity and never makes a suspected behavioral bug a Nit. Reserve Nit strictly for maintainability items with no possible behavior impact.' Delete 'or a nit' from SKILL.md line 66.

## HIGH (12)

### Uncertain-but-real bugs are routed to 'nit' and disappear; the skill has ~6 precision guardrails and no recall counterweight
- **file**: `.claude/skills/code-review/SKILL.md`  |  **category**: recall-gap
- **evidence**: Line 66: 'Only claim something is a bug if you can name how it breaks; otherwise mark it as a question or a nit.' Plus rubric lines 15-16 ('at least High only if you can name a concrete input/state ... If you can't, it's a Question or a Nit'), line 3-4 ('pick the lower one', 'over-flagging erodes trust'), and SKILL lines 47-48, 70-71, 82, 20-21 — a heavy, one-sided anti-flagging gradient.
- **なぜ品質を下げるか**: A model following conservative instructions literally will, when it has a real but unproven suspicion (a plausible race, a suspicious unchecked cast), take the 'or a nit' exit and file it as a Low nit — which maintainers skip. The '...or a nit' phrasing lets a genuine serious suspicion be demoted to noise instead of preserved. With no instruction anywhere to err toward surfacing high-consequence suspicions, recall on hard-to-confirm bugs (concurrency, security, data loss) collapses.
- **提案**: Remove the 'or a nit' escape for suspected real defects: route unconfirmed-but-plausible issues to 'Question', never to 'Nit'. Add one explicit recall instruction: 'If you genuinely suspect a security, data-loss, or concurrency bug but cannot fully confirm it from the diff, raise it as a Question at the severity it would carry if true — do not drop it or bury it as a nit. Missing a real critical is worse than one well-reasoned Question.'

### Reading surrounding code is motivated only by false-positive avoidance; no instruction to grep call sites to find newly-broken consumers
- **file**: `.claude/skills/code-review/SKILL.md`  |  **category**: mechanism
- **evidence**: Section 2 (lines 44-48) frames opening surrounding code entirely around precision: 'Most false-positive review comments come from judging a hunk without reading the function it lives in.' The skill grants Grep and Glob but never tells the reviewer to enumerate callers/usages of a changed symbol. Scope is 'the changed lines and what they touch' (line 54) with no method for finding what touches them.
- **なぜ品質を下げるか**: The most common consequential diff bug — changing a function's signature, return contract, nullability, or units, then leaving an unchanged call site broken — lives OUTSIDE the diff by definition. A reviewer who reads surroundings only 'to avoid false positives' reads the changed function defensively and never greps for the twelve callers that now pass the wrong argument order or ignore a newly-returned error. The available Grep tool goes unused for its highest-value purpose.
- **提案**: Add a recall-motivated step: 'When a change alters a function's signature, return value, nullability, units, thrown errors, or side effects, Grep for its call sites and read them — an unchanged caller relying on the old contract is a bug the diff introduced. Read surroundings not only to avoid false positives but to find consumers the change breaks.'

### Finding format never requires stating the severity label, only 'most-severe first' ordering
- **file**: `.claude/skills/code-review/SKILL.md`  |  **category**: output-format
- **evidence**: "Score each finding with `references/severity-rubric.md` and report most-severe first. For every finding give: **file:line**, a one-line statement of the defect, and a concrete failure scenario (input/state → wrong result)." — no instruction to print the Critical/High/Medium/Low/Question tag itself. Same omission is repeated verbatim in `.claude/commands/code-review.md` step 4.
- **なぜ品質を下げるか**: Ordering alone is a weak signal: a reader (or any downstream tool triaging findings) can't tell whether item #3 is a must-fix High or a borderline Medium without re-deriving it from the rubric themselves, and can't cheaply filter 'show me only Critical/High'. On a real 10-finding review this turns an otherwise well-calibrated rubric into invisible metadata — all the calibration work in severity-rubric.md never reaches the user in a labeled, actionable form.
- **提案**: Add to step 4: "For every finding give: **file:line**, its **severity label** (Critical/High/Medium/Low/Question), a one-line statement of the defect, and a concrete failure scenario." Apply the same addition to the parallel step 4 in `.claude/commands/code-review.md`.

### Destructive-operation / data-loss class is the #1 Critical in the rubric but has NO trigger in the checklist
- **file**: `.claude/skills/code-review/references/review-checklist.md`  |  **category**: coverage-gap
- **evidence**: The severity rubric's top Critical example (severity-rubric.md line 8) is 'Data loss ... corruption on the happy path', yet the checklist's 'Data & API contracts' section (lines 32-36) only mentions signatures, compatibility, migrations, and N+1. Nowhere does any checklist bullet cue destructive operations: DELETE/UPDATE without a WHERE clause, DROP/truncate in a migration, file overwrite/truncate, `rm -rf`, cache eviction of wrong keys, bulk mutation over an unbounded set.
- **なぜ品質を下げるか**: On a diff that adds `DELETE FROM sessions` (missing the `WHERE user_id = ?`) or a migration that drops a still-read column, a reviewer walking the checklist finds no category that says 'look for irreversible data destruction'. The single highest-consequence bug class has no recall hook, so it is systematically missed on exactly the diffs where it matters most.
- **提案**: Add explicit bullets to the checklist. Under a new 'Data loss' heading or within Data & API contracts: 'Destructive statement without a scoping predicate (DELETE/UPDATE/DROP/TRUNCATE with no or wrong WHERE; bulk op over an unbounded set).' 'Migration or code that drops/renames a column, key, or file still read elsewhere.' 'Overwrite/truncate that can clobber existing data; write that is not idempotent under retry.'

### Pre-existing-issue cap buries bugs the change newly makes reachable or triggerable
- **file**: `.claude/skills/code-review/references/severity-rubric.md`  |  **category**: railroading
- **evidence**: Line 18-19: 'Pre-existing issues outside the diff are capped at Low unless the change makes them materially worse.' Reinforced by SKILL.md line 84 ('Pre-existing issues outside the changed lines are at most a brief aside') and line 54 ('do not review the whole codebase').
- **なぜ品質を下げるか**: When a diff adds a new caller that routes attacker-controlled input into an existing `parseAmount()` with a latent integer overflow, or adds a new enum case that an unchanged `switch` elsewhere silently mishandles, the defect technically lives on unchanged lines. A conservative model reads 'pre-existing, cap at Low' and files a now-exploitable/now-triggered bug as an optional nit. 'Materially worse' is ambiguous and the whole skill pushes ambiguity downward, so genuinely change-activated bugs get suppressed.
- **提案**: Add a carve-out: 'A latent defect that the change newly makes reachable, triggerable, or exercised with untrusted input is scored at its true severity, NOT capped — the change owns bugs it activates. The Low cap applies only to defects the change neither touches nor exposes.'

### "At least High" rule requires a 'wrong result', but the table's own High examples (resource leaks) don't produce one
- **file**: `.claude/skills/code-review/references/severity-rubric.md`  |  **category**: severity-calibration
- **evidence**: "A finding is at least **High** only if you can name a concrete input/state that produces a wrong result. If you can't, it's a **Question** or a **Nit**." — directly contradicts the High row's own example: "lock not released, missing rollback".
- **なぜ品質を下げるか**: A reviewer following the literal rule of thumb over the table will downgrade genuine High-severity findings (unreleased locks, unclosed file handles/connections, missing rollback on partial failure) to Nit or Question because a resource leak under normal operation doesn't produce an immediately-observable 'wrong result' — it produces exhaustion/deadlock over time or under load. Since the model is known to follow conservative literal instructions, this specific wording will systematically suppress recall on exactly the leak/rollback bugs the rubric lists as canonical High-severity findings, e.g. a DB connection acquired in a new code path with no `finally`/`defer` release on the error branch.
- **提案**: Split the rule of thumb into two clauses: "A finding is at least High if you can name a concrete input/state that produces a wrong result, OR a concrete operation/path that leaks a resource, breaks an invariant, or leaves data/state inconsistent, even if the visible symptom only appears after repetition or under load. If neither applies, it's a Question or a Nit."

### The 'pre-existing issues capped at Low' rule suppresses bugs the diff newly activates
- **file**: `.claude/skills/code-review/references/severity-rubric.md`  |  **category**: severity-calibration
- **evidence**: severity-rubric.md lines 17-18: 'Pre-existing issues outside the diff are capped at Low unless the change makes them materially worse.' reinforced by SKILL.md lines 83-84: 'Respect the diff's scope. Pre-existing issues outside the changed lines are at most a brief aside, not the review.'
- **なぜ品質を下げるか**: The common real case is a changed line that newly routes untrusted input into a pre-existing sink: the added code does `query(userInput)` where `query()` is an existing unsanitized function. A literal reader sees the vulnerability 'lives' in pre-existing code and caps it at Low / brief-aside, when in fact the diff just turned a dormant function into a live SQL-injection. The Low cap is stated forcefully and first; the 'materially worse' escape hatch is a subordinate clause a conservative model will under-apply. Result: the review's most important finding gets demoted to a footnote.
- **提案**: Invert the emphasis. Lead with: 'If the changed code reaches, calls, triggers, or newly exposes a pre-existing issue, score it at the FULL severity of the resulting behavior — the bug is effectively introduced by this change. Only issues the diff neither touches nor activates are capped at Low.' Give a worked example of new code passing input into an existing unsanitized query being Critical, not Low.

### Pressure is one-directional (precision only); nothing counterweights suppression of true positives
- **file**: `.claude/skills/code-review/references/severity-rubric.md`  |  **category**: recall-gap
- **evidence**: Stacked conservative directives with no recall counterpart: rubric line 4 'When unsure between two levels, pick the lower one', line 5 'over-flagging erodes trust in the review', line 12/16 demotion rules; SKILL.md line 21 'not a lint dump and not vague praise', line 66 gate, lines 70-71 'if the change is clean, say so plainly and stop. A short review of a good diff is a success'. Every thumb on the scale pushes toward reporting LESS.
- **なぜ品質を下げるか**: Known model behavior: an AI follows conservative-reporting instructions literally, and here they are unopposed. On a diff containing one subtle real bug plus nothing else, the model has five instructions telling it to stay quiet or downgrade and zero telling it that a missed real bug is the worse failure. The expected outcome is silence on genuine defects — the skill optimizes precision into a recall hole. The 'clean diff is a success' line, with no floor, actively rewards declaring victory.
- **提案**: Add an explicit recall counterweight of equal force, e.g.: 'The worst outcome of a review is a real, consequential bug you saw signs of but did not surface. When you notice a plausible defect you cannot fully confirm, raise it as a Question rather than dropping it — an explained Question that turns out fine costs the reader seconds; a missed bug costs an incident. Silence is only correct after you have actually traced the changed lines and their callers.'

### No truncation detection or warning for large diff output
- **file**: `.claude/skills/code-review/scripts/collect-diff.sh`  |  **category**: mechanism
- **evidence**: Lines 81, 85: `git diff --stat $diff_args` and `git diff $diff_args` called with no size limit or overflow handling. Script outputs full unified diff without checking output size.
- **なぜ品質を下げるか**: When a very large file (10MB JSON, binary, or generated code) is in the changes, the unified diff can overflow the AI reviewer's context window (typically 200K tokens). The reviewer sees only the first N% of the diff and believes it's complete, missing crucial changes in the unseen portion. For example: a 5MB config file change would produce massive diff output; the reviewer reads the first 50KB visible, thinks they've reviewed it, but misses the malicious code injection in the final 4,950KB.
- **提案**: Add a check after generating the diff: Count output lines or bytes; if > threshold (e.g., 10000 lines), emit a warning before the diff output: `echo '⚠️ WARNING: Diff output exceeds 10,000 lines — review may be incomplete. Run locally with: git diff <ref> | less'` to alert the reviewer and provide an escape hatch.

### Binary file changes shown as 'Binary files differ' with no guidance for reviewer
- **file**: `.claude/skills/code-review/scripts/collect-diff.sh`  |  **category**: mechanism
- **evidence**: Script calls `git diff` which outputs 'Binary files a/file differ' for binary files. No detection, filtering, or guidance. SKILL.md Gotchas section (lines 73-86) does not mention binary files.
- **なぜ品質を下げるか**: When a binary file (PNG, PDF, compiled .so, .jar, etc.) changes, the reviewer sees 'Binary files a/logo.png and b/logo.png differ' with no content. They have no way to understand what changed: file size, corruption, format change, etc. Reviewer may not realize the binary change needs separate inspection and approves without checking. Example: A malicious .so library is swapped in; diff shows 'Binary files differ'; reviewer approves thinking there's nothing to review.
- **提案**: Detect binary files from `git diff --stat` output and explicitly surface them. Before the unified diff, list detected binary files: `echo '--- Binary files (content not shown, inspect manually) ---'; git diff --stat $diff_args | grep -E 'Binary|bin$' | awk '{print $1}'`. Add guidance to SKILL.md Gotchas: 'Binary files show as changed but no content is visible — use `git show HEAD:file` and your tools to manually inspect binary changes.'

### "try/catch too broad" checklist item has no bar for actual harm, inviting reflexive flags on defensive/intentional broad catches
- **file**: `references/review-checklist.md`  |  **category**: false-positive-risk
- **evidence**: "`try/catch` too broad, hiding failures it shouldn't." (Control flow & errors section) — no guidance distinguishing an intentional top-level error boundary or defensive catch from one that actually masks a real failure.
- **なぜ品質を下げるか**: Broad catch blocks (e.g., a top-level request handler catching Exception to return a 500, or a background job wrapping its loop body to keep processing other items) are extremely common, deliberate patterns. Without a rule requiring the reviewer to show the specific failure it hides and why that failure matters here, the checklist phrasing alone is enough to make a conscientious reviewer flag every broad catch it sees in a changed function as a maintainability/correctness concern — a textbook nit-as-blocker that a maintainer will reject on sight, eroding trust in the rest of the review.
- **提案**: Tighten the bullet to require evidence: "`try/catch` broader than needed *and* the reviewer can name a specific error type it would swallow that the caller needed to see (e.g., a caller checks a specific exception/error code that can no longer surface). A catch that logs-and-rethrows, or that exists as an intentional boundary, is not a finding."

### Severity rubric contains a self-contradicting rule that resolves toward inflation on security findings
- **file**: `references/severity-rubric.md`  |  **category**: severity-calibration
- **evidence**: "When unsure between two levels, pick the lower one and say why" (line 4) directly conflicts with "Security and data-loss findings default up a level, not down" (line 17), with no tie-breaker given for the case where both apply.
- **なぜ品質を下げるか**: On a diff with a security-adjacent pattern the reviewer isn't sure about (e.g., string-built SQL whose input source isn't fully traced, or a new field written into a log call), the model has two contradictory instructions to reconcile. Given known model behavior toward literal, salience-driven rule-following, the more emphatic-sounding rule ("default up") tends to win, so an unconfirmed suspicion gets reported as Critical/High "SQL injection" or "secret logged" rather than the Question/Nit the exploitability rule would assign. This produces exactly the false-positive-with-inflated-alarm pattern the north star warns against: a loud, wrong finding on code that turns out to be internal-only or already sanitized upstream.
- **提案**: Make the interaction explicit: "Security and data-loss findings default up a level *only once the exploitability rule above is satisfied* (you can name the concrete input/state). Do not use this rule to promote an unconfirmed suspicion past Question/Nit merely because it touches a security-sensitive area — an unverified security worry is still a Question, not a Critical."

## MEDIUM (15)

### Pre-existing/out-of-scope findings have no required separation from the ranked severity list, so they can inherit a severity level they shouldn't have
- **file**: `.claude/skills/code-review/SKILL.md`  |  **category**: railroading
- **evidence**: Step 2 instructs "open the surrounding code" broadly, while the Gotchas section only says pre-existing issues are "at most a brief aside, not the review" — there is no instruction that such asides must be excluded from the severity-ranked list or denied a rubric level.
- **なぜ品質を下げるか**: Reading surrounding code (step 2) is exactly how a reviewer stumbles onto pre-existing bugs unrelated to the diff. Nothing stops the model from adding "Medium: pre-existing off-by-one in helper()" into the same ranked list as real diff findings, capped only by the rubric's "capped at Low unless the change makes them materially worse" — which still permits a Low entry sitting in the primary findings list. That inflates the appearance of the diff having issues it introduced, when the reviewer actually found something unrelated, misdirecting the maintainer's fix effort toward code the PR didn't touch.
- **提案**: Add to step 4 or Gotchas: "Pre-existing issues you notice while reading context go in a separate 'Out of scope' note after the ranked findings, never inside the severity-ranked list itself, and never with a rubric level attached — the ranked list is reserved for issues introduced or touched by this diff."

### Weighting examples in §3 cue only injection/authz/parsing/refactor — never concurrency, data-loss, or crypto
- **file**: `.claude/skills/code-review/SKILL.md`  |  **category**: coverage-gap
- **evidence**: Lines 56-59: 'a SQL query → injection and N+1; an auth path → access control; a parser → malformed input; a refactor → behavior preservation.' All four worked examples steer toward correctness/injection classes. None cue the invisible-in-hunk classes: shared state → race, background job/webhook → idempotency, migration/delete → data loss, token/hash → crypto misuse.
- **なぜ品質を下げるか**: Concurrency, idempotency, and crypto bugs look locally fine — nothing in the hunk is wrong on its face, so they are only found if the reviewer is actively primed to look for them. By giving four examples that all point at the easy-to-see classes, the skill anchors the model's attention there and leaves the checklist's own Concurrency section under-weighted precisely when the diff touches threads, locks, or async.
- **提案**: Add examples covering the invisible classes: 'shared mutable state or async → races and unawaited work; a webhook/retry/payment path → idempotency and double-processing; a delete/migration → data loss and reversibility; token/password/randomness → crypto misuse. These rarely look wrong in the hunk — you must actively test them against the code.'

### 'Clean diff = success' is granted with no minimum-effort gate, enabling a lazy shortcut to 'looks good'
- **file**: `.claude/skills/code-review/SKILL.md`  |  **category**: output-format
- **evidence**: SKILL.md lines 70-71: 'Keep it honest: if the change is clean, say so plainly and stop. A short review of a good diff is a success, not a failure.' The 'Understand before judging' step (lines 44-48) is described but not made a precondition of concluding 'clean.'
- **なぜ品質を下げるか**: Because raising any finding is gated behind multiple hurdles while declaring the diff clean is explicitly praised as success, the path of least resistance is to skim the unified diff and pronounce it good without ever opening the surrounding functions the skill told it to read. The model can satisfy the letter of the skill (short, honest, no false positives) while doing none of the analysis that would catch the bug. This converts an honesty instruction into a recall failure.
- **提案**: Condition the clean verdict on the analysis actually being done: 'You may conclude the diff is clean only after you have opened and traced each non-trivial hunk and its callers per step 2. State briefly what you checked (e.g. "traced the two changed functions and their two call sites; boundary and error paths hold") so "looks good" is an earned conclusion, not a skip.'

### Security checklist omits crypto misuse, ReDoS/input-driven resource exhaustion, and object-level authz (IDOR)
- **file**: `.claude/skills/code-review/references/review-checklist.md`  |  **category**: coverage-gap
- **evidence**: Security section (lines 20-25) lists injection, missing authN/authZ on a NEW endpoint, hard-coded secrets, path traversal/SSRF/deserialization/XSS, and weak input validation. It does not mention: weak/misused cryptography (MD5/SHA1 for passwords, static IV, ECB, `Math.random()` for tokens), ReDoS or unbounded-input resource exhaustion, or object-level access control / IDOR (authenticated user accessing another user's object via an id parameter on an existing endpoint).
- **なぜ品質を下げるか**: A diff that adds `hashlib.md5(password)` or builds a session token from a non-CSPRNG, or adds a `?userId=` lookup with no ownership check on an already-authenticated route, passes the checklist clean — 'missing authorization on a NEW endpoint' does not fire for an IDOR on an existing one, and no crypto bullet exists at all. These are common, high-severity security defects the reviewer is not prompted to catch.
- **提案**: Add Security bullets: 'Weak or misused crypto: fast/broken hash for passwords, non-CSPRNG for tokens/IDs, static/reused IV or nonce, ECB mode, home-rolled crypto.' 'Object-level access control: does the handler verify the authenticated user owns the object referenced by an id/param (IDOR), not just that they are logged in?' 'Untrusted input driving unbounded work: catastrophic-backtracking regex (ReDoS), unbounded allocation/loop sized by request data.'

### No checklist dimension for dependency / supply-chain changes
- **file**: `.claude/skills/code-review/references/review-checklist.md`  |  **category**: coverage-gap
- **evidence**: The checklist has Correctness, Control flow & errors, Security, Concurrency & state, Data & API contracts, Performance, Tests, Maintainability — no category for added/upgraded third-party packages (unpinned/loose version ranges, known-vulnerable or abandoned packages, license changes, typosquat-risk new deps).

Without a checklist line pointing at this, and given the Gotchas section explicitly tells the reviewer lockfiles are 'noise, don't line-review them' (SKILL.md), the natural reading bleeds into skipping the manifest file itself too — leaving a whole class of supply-chain risk with zero systematic scrutiny.
- **提案**: Add to `review-checklist.md` under Data & API contracts or a new short section: "## Dependencies — New or bumped third-party packages: pinned/reasonable version range, no known-bad/abandoned package, license compatible, diff between old/new version isn't a major bump smuggled in as a patch." And clarify in SKILL.md's Gotchas that only the generated lockfile body is noise — the manifest entries that changed still deserve a look.

### No idempotency / duplicate-invocation dimension under Concurrency & state
- **file**: `.claude/skills/code-review/references/review-checklist.md`  |  **category**: coverage-gap
- **evidence**: "## Concurrency & state" lists only: shared mutable state/races, unawaited promises/unhandled rejection, deadlock/lock-ordering/TOCTOU. Nothing about handlers that must tolerate being invoked more than once (webhooks, queue consumers, retried HTTP requests, payment/charge operations).
- **なぜ品質を下げるか**: Double-processing bugs are one of the most consequential and common real-world defect classes in backend diffs — e.g. a new webhook handler or queue consumer that charges a card, sends an email, or decrements inventory with no idempotency key/dedup check, so an at-least-once delivery retry causes a double charge or double side effect. This is neither a race (single invocation, no concurrent threads needed) nor covered by any other line item, so the checklist gives no cue to look for it even on diffs whose name/commit message make the risk obvious (e.g. 'handle payment webhook').
- **提案**: Add a bullet to Concurrency & state: "Operations that must be idempotent (webhook handlers, queue consumers, retried requests, payment/charge/inventory mutations) — is there a dedup key, unique constraint, or check-before-act guard against duplicate invocation?"

### 'Weight toward matching categories / skip the ones that don't fit' causes tunnel vision on off-type bugs
- **file**: `.claude/skills/code-review/references/review-checklist.md`  |  **category**: railroading
- **evidence**: review-checklist.md line 3: 'Apply the categories that fit the change; skip the ones that don't.' plus SKILL.md lines 56-58 giving the mapping 'a refactor → behavior preservation.'
- **なぜ品質を下げるか**: A model told a PR is 'a refactor' will weight only toward behavior-preservation and literally 'skip' Security and Concurrency as not-fitting. But refactors routinely smuggle in real defects off their nominal axis — a rename that also concatenates user input into a shell command, a move that drops a lock. Instructing the model to skip categories by the change's apparent label creates a blind spot exactly where the dangerous surprises hide.
- **提案**: Keep the weighting but carve out a floor: 'Weight toward the matching categories, but Security and data-loss are never skipped regardless of what the change appears to be — scan every hunk for an untrusted-input-to-sink path and for dropped error/resource handling even in a pure refactor.'

### Medium row conflates 'missing test for new behavior' with actual behavioral bugs and contract risk
- **file**: `.claude/skills/code-review/references/severity-rubric.md`  |  **category**: severity-calibration
- **evidence**: "**Medium** | Bug on an edge case, missing test for new behavior, or a contract risk. Fix soon. | Unhandled empty input, N+1 query, breaking API change without a version bump, missing migration reversibility."
- **なぜ品質を下げるか**: A pure process gap ('this new function has no test') and a live behavioral bug ('empty input crashes') are different kinds of finding with different urgency, yet the rubric puts them at the identical severity level, so they compete for the same ranked slot in the report. Combined with 'when unsure between two levels, pick the lower one', a reviewer weighing an edge-case bug against a test-gap at the same tier has no calibration cue for which to rank higher, and a review of a diff with several missing-test notes but no real bugs can read as more alarming ('4 Medium findings!') than it should, diluting signal on reviews where the actual bugs matter more.
- **提案**: Split into two rows or sub-bullets: keep 'edge-case bug / contract risk without version bump' at Medium, and move plain 'missing test coverage for new behavior' to its own Low-ish or explicitly-separate note (e.g. "Medium-test-gap: report separately from behavioral findings, don't let it inflate the Medium bug count").

### Untracked new files are surfaced only as filenames, so the highest-bug-density code is easily skipped
- **file**: `.claude/skills/code-review/scripts/collect-diff.sh`  |  **category**: coverage-gap
- **evidence**: Lines 87-95 print untracked files as a bare name list under '--- Untracked (new) files, not in the diff above — review these too ---'. ### Git config can alter diff output format without reviewer awareness
- **file**: `.claude/skills/code-review/scripts/collect-diff.sh`  |  **category**: mechanism
- **evidence**: Lines 81, 85: `git diff` called without explicit format options like `--no-color`, `--no-ext-diff`, or `--algorithm`. User's git config (diff.algorithm, color.diff, diff.colorMoved, etc.) can change output.
- **なぜ品質を下げるか**: If a user has `diff.algorithm=patience` or `diff.algorithm=histogram` set in their git config, the diff hunks shown can differ significantly from the default algorithm, showing different context or combining/splitting hunks. ### File mode and permission changes not explicitly surfaced or easy to miss

### Default branch detection falls back silently to 'main' even if it doesn't match repo's actual default
- **file**: `.claude/skills/code-review/scripts/collect-diff.sh`  |  **category**: mechanism
- **evidence**: Lines 23-37: `default_branch()` function tries origin/HEAD, then a hardcoded list [main, master, trunk, develop], then echoes 'main' unconditionally as fallback (line 37) even if no matching branch exists locally.
- **なぜ品質を下げるか**: In a repository where the actual default branch is 'staging' or 'release-v2' (not in the hardcoded list), the function returns 'main'. If a local 'main' exists (even if stale), the mechanism silently compares against it. The reviewer sees 'branch vs origin/main (merge-base: abc)' but origin/main might be months old. - **提案**: Add validation: After the fallback to 'main', check if it actually exists: `if ! git show-ref --verify --quiet "refs/remotes/origin/$db" 2>/dev/null && ! git show-ref --verify --quiet "refs/heads/$db" 2>/dev/null; then echo "error: Could not determine default branch. ### "Duplication that already exists elsewhere" can be asserted without any instruction to verify it via search
- **file**: `references/review-checklist.md`  |  **category**: false-positive-risk
- **evidence**: "Duplication that already exists elsewhere and could be reused." (Maintainability) — the skill gives Grep/Glob as allowed tools but nowhere requires using them to confirm this specific claim before writing it down.
- **なぜ品質を下げるか**: This is the one checklist item that inherently claims knowledge of code outside the diff ("already exists elsewhere"). ### The Question severity tier is unbounded, letting speculative doubts accumulate as reportable findings
- **file**: `references/severity-rubric.md`  |  **category**: noise
- **evidence**: "**Question** | You suspect an issue but can't confirm it from the diff." — this tier is offered as a legitimate, always-available escape valve with no cap on count or bar for materiality, unlike every other tier which requires naming a concrete input/state.
- **なぜ品質を下げるか**: Because SKILL.md explicitly tells the reviewer to downgrade anything it can't fully substantiate into a Question rather than drop it ("Only claim something is a bug if you can name how it breaks; otherwise mark it as a question or a nit"), the safe, encouraged move for every half-formed doubt encountered while reading is to keep it as a listed Question.
