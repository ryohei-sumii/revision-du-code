## 壁打ち(反証 2件)

### 1. verdict=**revise**  recall:neutral / precision:improves / data支持:True / 既出:False
- 反論: Two attacks on this proposal. (1) Overfitting: all 3 "repeated" FP instances are the *same* planted trap in the *same* fixture (reachability-sqli), triggered by 3 different models — that's one data point about one trap, not three independent confirmations of a generalizable reviewer failure mode. The "3 of 4 FPs" framing overstates the breadth of evidence. (2) Recall risk: the proposed bullet (b) says a missing-range-validation value bound via '?' "is at most a Low robustness nit... not a security or Medium finding," and characterizes the outcome as "a crash or odd-but-bounded result." But the checklist already has a distinct, legitimate Medium-severity category one section down: "N+1 queries, unbounded result sets, missing pagination or index." A `LIMIT ?` fed an unvalidated huge value (e.g. `2**63-1`) is not a security/injection bug, but it IS a textbook unbounded-result-set / resource-exhaustion bug — exactly the class the aggregate data shows models are already under-catching (`misses_by_class: resource-exhaustion:1`). As written, the blanket "not... Medium" language would train reviewers to wave off genuine resource-exhaustion findings on the same line, directly cutting against the one recall gap the data already shows.
- 応答: The core diagnosis is right and worth fixing: "parameterized ≠ unvalidated" is a real, well-known confusion (SQLi-focused training makes reviewers pattern-match on "user input near a query" regardless of whether it's interpolated or bound), and the fixture evidence, while narrow, is a clean illustration of it recurring across three different models on one instance — consistent with, not just an artifact of, that known failure mode. The fix is directionally sound and should ship, but the resource-exhaustion carve-out must be made explicit or the rule will oscillate the aggregate's recall on the very miss class it already under-catches. Scope the "not a security/Medium finding" claim strictly to the injection axis, and explicitly route unbounded-value concerns to the existing unbounded-result-set bullet so the two categories don't get conflated by a single new sentence.

### 2. verdict=**revise**  recall:neutral / precision:improves / data支持:True / 既出:False
- 反論: Two attacks. (1) Overfitting: the change is justified by exactly one of four measured FPs (reachability-sqli/opus IDOR-High), a single model on a single fixture — thin evidence for a bespoke, auth-specific worked example baked into the skill. The other 3 FPs are a different class (benign-trap over-flagging on the limit param, plus a hedged nit) that this proposal does nothing for, so it addresses only 25% of the precision leak. (2) Recall/philosophy risk: the proposal's remedy is to *reframe as a Question*, but the skill's core method (§2 'Understand before judging,' Grep the call sites) is to *verify, not hedge*. The right first move on a suspected missing-auth is to Grep for the decorator/middleware/guard layer, then conclude. As written ('do not claim missing auth... when you have not seen the guard layer — raise it as a Question'), it can be read as license to downgrade a genuinely confirmable auth bug — endpoint fully shown, no guard found anywhere on search — to a mere Question, a marginal recall hit. It also partially duplicates §4's existing 'unconfirmed → raise as a Question at the severity it would carry' sentence.
- 応答: The overlap is partial, not fatal: §4 states the general unconfirmed→Question rule, yet the FP still occurred because severity-rubric.md pulls the opposite way ('Security... default up a level, not down, including ones you can only raise as a Question') and §2's reachability carve-out invites a High. A reviewer following those literally lands on a definite High for an unseen auth gap — which is precisely the measured FP. So an explicit converse that names the auth-middleware-not-in-diff pattern resolves a real internal tension rather than merely repeating existing text. The recall objection is answered by requiring verification first: if the guard layer is searched and confirmed absent, the reviewer keeps High; only genuinely-unverifiable cases fall to a High-tier Question, which the rubric already ranks alongside confirmed findings, so nothing is silenced. Precision strictly improves (removes false certainty) with no plausible new FP. Net: keep the idea, tighten the wording.
